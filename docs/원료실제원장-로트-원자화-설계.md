## 1. 결론

현재 `items` 문서가 품목정보·원가·재고·로트를 모두 들고 있고, 실제 원장
`rawMaterialLedger`는 화면과 서비스 여러 곳에서 따로 쓰인다. 이 상태에서 쓰는 순서만
고쳐서는 새 경로가 생길 때 다시 갈린다.

최종 구조는 실제 재고 코어와 서류 후처리로 나눈다.

```text
┌─ 실제 재고 코어 ───────────────────────────────────────────────────────────┐
│ rawInventories/{companyId}__{rawItemId}  현재 상태: stockKg + 활성 로트   │
│ rawMaterialLedger/{operationId}          변경 이력: 입고·사용·실사·취소   │
│ rawInventoryJobs/{jobId}                 여러 원료 작업의 진행 상태        │
└────────────────────────────────────────────────────────────────────────────┘
                 │ 성공한 결과를 읽기 전용 입력으로 제공
                 ▼
┌─ 서류 후처리 ──────────────────────────────────────────────────────────────┐
│ 실제 입고 movement + 배송완료 판매자료 + rawDocEntries(서류 손입력)       │
│                         ↓                                                  │
│                  buildRawDocSheetFor()                                     │
│                         ↓                                                  │
│ 원료수불부·생산판매기록부·생산작업기록부                                  │
└────────────────────────────────────────────────────────────────────────────┘
```

- `rawInventories`가 현재 재고의 유일한 근거다.
- `rawMaterialLedger`는 지우거나 덮어쓰지 않는 이력이다.
- `rawInventoryJobs`는 주문 생산처럼 여러 원료가 차례로 처리될 때 어디까지 끝났는지 기록한다.
- 수량 변경은 `executeRawInventoryCommand()` 하나만 한다.
- 서류용 `rawDocEntries`와 제품 재고·제품 로트는 재고 코어에 섞지 않는다.
- 재고 코어는 서류가 없어도 완결된다. 서류 계산 실패는 재고 transaction을 되돌리지 않는다.
- 서류는 실제 재고를 쓰지 않고, 성공한 실제 원장과 판매자료를 읽어 다시 만들 수 있어야 한다.

## 2. 지켜야 하는 등식

원료 하나의 현재 상태는 언제나 다음과 같아야 한다.

```text
rawInventories.stockKg = rawInventories.activeLots의 kgRemaining 합
실제 원장 마지막 잔량 = rawInventories.stockKg
```

기름도 저장은 kg이다. L는 입력·표시할 때만 밀도로 바꾼다.

`items.stock`과 `items.lots`는 이관 기간에만 호환용으로 읽고, 최종적으로 원료 품목에서는
없앤다. 같은 재고를 두 문서에 계속 복제하면 어느 쪽이 진짜인지 다시 갈린다.

현재 `lotsAreTotal`은 로트는 벌크+포장 총량, `stock`은 벌크만 뜻하게 만들어 위 등식을 깬다.
기존 [OEM-임가공-설계.md](OEM-임가공-설계.md)의 “재고는 품목별 실물, 종합은 서류에서만”
결정대로 원료 상태에는 **실제로 벌크 홀더에 남은 로트만** 둔다. 포장품은 자기 품목 재고와
제품 로트가 맡고 `lotsAreTotal`은 이관 뒤 제거한다.

## 3. 왜 로트를 별도 문서로 쪼개지 않는가

로트마다 Firestore 문서를 만들면 보기에는 정규화되지만 FIFO 한 번에 여러 로트를 읽고 고쳐야
한다. 입고와 생산이 동시에 실행될 때 query 결과와 차감 순서를 transaction 안에서 일관되게
다루기도 복잡해진다.

이 앱의 원료 한 종류에서 동시에 살아 있는 로트 수는 크지 않다. 따라서
`rawInventories` 한 문서 안에 **활성 로트와 최근 소진 로트만 배열로** 두는 편이 안전하다.
그 문서 하나가 원료별 직렬화 지점이 된다.

- 소진 후 보존기간이 지난 로트는 상태 문서에서 제거한다.
- 어느 로트에서 얼마가 빠졌는지는 원장 이벤트의 `lotChanges`에 영구 보존한다.
- 문서 크기와 활성 로트 개수를 진단에서 측정하고 상한 경고를 둔다.
- 실제 규모가 문서 한도를 위협할 때만 서버 transaction + 로트 하위 컬렉션으로 옮긴다.

## 4. 현재 상태 문서

```ts
type RawInventoryState = {
  id: string;                    // `${companyId}__${rawItemId}`
  companyId: CompanyId;
  rawItemId: string;
  materialSnapshot: string;      // 표시용. **서비스가 rawItemId로 조회해 채운다**
  stockKg: number;               // 직접 입력하지 않는다 — activeLots 합계를 매번 다시 센다
  activeLots: RawMaterialLot[];  // FIFO 대상
  recentDepletedLots: RawMaterialLot[];   // 화면 표시용 꼬리. **복원은 여기 의존하지 않는다**
  stocktakeAnchor?: {            // 마지막 실사 한 묶음
    effectiveAt: string;
    operationId: string;
    sequence: number;
  };
  revision: number;              // 정상 적용된 명령 수. applied일 때만 +1
  lastProcessedAt: string;       // 마지막 명령을 처리한 시각. 수량이 안 변한 소급도 갱신
};
```

`companyId`와 `rawItemId`가 필수다. **원료명은 화면이 준 값을 믿지 않는다** — 서비스가
`rawItemId`로 품목을 읽어 `materialSnapshot`을 채운다. `items/{rawItemId}`는 품목명·단위·밀도·
분류 같은 기준정보만 맡는다.

`revision`은 **앱 배포 버전이 아니다.** 그 원료에 정상 적용된 명령 수이며, 언제나
`revision === 가장 최근 Movement.sequence`다. `duplicate`·`conflict`·`rejected`는 올리지 않고,
수량이 0인 소급 입력은 이력이 적용됐으므로 **올린다.**

`recentDepletedLots`는 화면이 `items.lots`(활성+소진)를 보는 이관 기간의 꼬리일 뿐이다.
**되돌리기는 이 배열을 쓰지 않는다** — 40개 밖으로 밀려난 로트도 복원해야 하므로 이력의
`lotChanges`에 담긴 스냅샷으로 되살린다(§9).

## 5. 변경 이력 문서가 중복 방지 표다

`rawMaterialLedger/{operationId}`는 실제 원장 줄이자 해당 작업이 이미 적용됐다는 증거다.
별도 완료표를 두면 완료표와 원장이 다시 갈릴 수 있으므로 원료별 수량 작업에는 이 문서를
그대로 사용한다.

```ts
type RawInventoryMovement = {
  id: string;                    // operationId와 같음
  operationId: string;
  companyId: CompanyId;
  rawItemId: string;
  materialSnapshot: string;
  commandHash: string;           // 명령 내용의 지문 — 같은 id 인데 내용이 다르면 conflict
  effectiveAt: string;           // 현실에서 일어난 업무 시각. 기간별 원장 기준
  recordedAt: string;            // DB 에 기록된 시각. 늦게 넣은 자료를 찾는 감사 기준
  sequence: number;              // 상태 revision 과 같은 적용 순번
  kind: 'receive' | 'consume' | 'stocktake' | 'deplete-lot' | 'reverse' | 'opening';
  reportedDeltaKg: number;       // 업무 기록 수량: 입고 +, 사용 -
  appliedDeltaKg: number;        // 이번에 현재 상태를 실제로 움직인 수량. 소급이면 0
  balanceAfterKg: number;        // effectiveAt 순 잔액이 아니라 sequence 적용 직후 잔액
  targetKg?: number;
  lotChanges: LotChange[];
  source: { type: string; id: string };
  reversalOf?: string;
  backdatedBeforeStocktake?: boolean;
  actorId?: string;
  actorName?: string;
};
```

`lotChanges`는 **되돌리기의 유일한 근거**다. 로트마다 `beforeKg`·`afterKg`를 적고, 그 명령이
건드린 로트의 **전체 모습(`lotSnapshot`)**도 같이 남긴다. 상태 문서의 `recentDepletedLots`는
40개까지만 들고 있어서, 그보다 오래 전에 소진된 로트는 상태만 보고는 되살릴 수 없다.

```ts
type LotChange = {
  lotId: string;
  beforeKg: number;
  afterKg: number;
  /** 그 명령이 건드리기 **직전**의 로트 전체. 소진돼 상태에서 빠진 로트도 이걸로 되살린다. */
  lotSnapshot: RawMaterialLot;
};
```

같은 `operationId` + **같은 `commandHash`**면 저장된 결과를 반환하고 재고를 다시 움직이지 않는다
(`duplicate`). 같은 `operationId`인데 **내용이 다르면** 조용히 통과시키지 않고 `conflict`로 막는다 —
예전에는 id 만 보고 넘겨서, 수량을 고쳐 다시 보낸 요청이 아무 일도 안 한 채 성공으로 보였다.

원장 이력은 수정·삭제하지 않는다. 오입력 취소는 원본을 가리키는 `reverse` 이벤트를 새로 만든다.

## 6. 쓰기 명령은 하나다

```ts
executeRawInventoryCommand(command): Promise<RawInventoryResult>
```

```ts
type RawInventoryCommand = {
  operationId: string;
  /** 명령 내용의 지문. 서비스가 만든다 — 부르는 쪽이 넘기지 않는다. */
  commandHash: string;
  companyId: CompanyId;
  rawItemId: string;
  effectiveAt: string;
  actorId?: string;
  actorName?: string;
  source: {
    type: 'purchase' | 'production' | 'manual' | 'adjustment' |
          'stocktake' | 'lot-delete' | 'reversal' | 'opening';
    id: string;
  };
} & (
  | { kind: 'receive'; kg: number; lot: ReceiveLotInput }
  | { kind: 'consume'; kg: number; mix?: MixRule }
  | { kind: 'stocktake'; targetKg: number }
  | { kind: 'deplete-lot'; lotId: string }
  | { kind: 'reverse'; originalOperationId: string }
);
```

**`materialSnapshot`은 입력에 없다.** 화면이 준 이름을 그대로 믿지 않고 서비스가 `rawItemId`로
품목을 읽어 채운다. 회사 범위도 같다 — 인증 문맥과 품목의 회사를 맞춰 본다.

**업무 한 건이 원료 여럿을 건드리면** 위 명령을 바로 부르지 않고 묶음으로 감싼다.

```ts
type RawInventoryBatchCommand = {
  jobId: string;                 // `production:{orderId}:{revision}` 처럼 업무 원본에서 만든 고정 id
  companyId: CompanyId;
  source: { type: 'production' | 'production-reversal' | 'oem'; id: string };
  commands: RawInventoryCommand[];
};
```

묶음은 `RawInventoryJob`을 만들고 원료별 명령으로 **분해**해 하나씩 실행한다. 원료별 트랜잭션은
각자 원자적이고, 전부 끝난 뒤에야 업무 원본(주문·생산)을 완료 처리한다(§8).

함수는 Firestore transaction 한 번에서 처리한다.

1. `rawMaterialLedger/{operationId}` · `rawInventories/{inventoryId}` · (reverse면) 원본 Movement와
   `reversalGuards/{원본 operationId}` 를 **모두 읽는다.**
2. 원장 문서가 이미 있으면 — `commandHash`가 같으면 `duplicate`(저장된 결과 그대로),
   **다르면 `conflict`**. 어느 쪽도 재고를 안 움직인다.
3. 회사·품목·수량·원본 작업을 검증한다. 실패는 `code`와 `message`로 돌려준다.
4. 새 로트 배열과 `stockKg`를 계산한다(순수 계산).
5. 상태의 `revision`을 1 올리고 그 값을 원장 `sequence`에 넣는다.
6. 상태 문서·원장 문서·(reverse면) `ReversalGuard`를 같은 transaction에서 쓴다.

원장 쓰기가 실패하면 상태도 안 바뀌고, 상태 쓰기가 실패하면 원장도 안 생긴다.

### 결과는 넷이다

```ts
type RawApplyResult =
  | { status: 'applied'; state: RawInventoryState; movement: RawInventoryMovement }
  | { status: 'duplicate'; movement: RawInventoryMovement }   // 같은 id + 같은 hash
  | { status: 'conflict'; movement: RawInventoryMovement }    // 같은 id + 다른 내용
  | { status: 'rejected'; code: RawRejectCode; message: string };
```

`rejected`는 **화면이 문구를 뜯어보지 않도록** `code`를 나눠 준다 —
`NOT_MIGRATED` · `STOCK_MISMATCH` · `TARGET_MISMATCH` · `LOT_NOT_FOUND` · `ORIGINAL_NOT_FOUND` ·
`ALREADY_REVERSED` · `RECEIPT_CONSUMED` · `INVALID_QUANTITY` · `MISSING_LOT_ID`.

transaction callback은 경합 시 여러 번 실행될 수 있다. 그 안에서는 알림, 화면 상태 변경,
`Date.now()`와 무작위 ID 생성을 하지 않는다. 작업 ID와 시각은 부르기 전에 한 번 정한다.

## 7. 작업 ID 규칙

| 업무 | `operationId` 예시 |
|---|---|
| 발주 입고 | `purchase:{poId}:{lineId}:{rawItemId}` |
| 주문 생산 | `production:{jobId}:{rawItemId}` |
| 생산 취소 | `reverse:{productionOperationId}` |
| 조정 요청 승인 | `adjustment:{requestId}:{rawItemId}` |
| 로트 삭제 | `lot-delete:{lotId}` |
| 최초 기초이월 | `opening:{inventoryId}` |
| 손입력·실사 | 모달을 열 때 UUID를 한 번 만들고 성공할 때까지 유지 |

Firestore 문서 ID 에 업무 원본 문자를 그대로 이어 붙이지 않는다. **치환·잘라내기는 충돌한다** —
`/` 를 `_` 로 바꾸면 `po1/x` 와 `po1_x` 가 한 문서가 되고, 길이로 자르면 앞이 같은 두 작업이
겹친다. 겹치면 뒤에 온 작업이 **`duplicate` 로 조용히 사라진다.**

그래서 `operationDocId()` 는 **해시로 만든다** — 사람이 읽을 수 있는 앞부분(안전한 문자만)에
원본 `operationId` 전체의 해시를 붙인다. 원본은 문서 안 `operationId` 필드에 그대로 남으므로
되짚을 수 있다.

손입력 UUID는 `useRef`와 `sessionStorage`에 보관한다. 응답 전에 새로고침해도 동일한 명령을
재전송할 수 있어야 한다.

## 8. 여러 원료를 묶는 작업 상태

원료별 transaction만 있으면 원장과 로트는 맞지만, 주문이 원료 세 종류 중 두 종류까지만
처리된 상태를 화면이 모를 수 있다. 그래서 `rawInventoryJobs`가 필요하다.

```ts
type RawInventoryJob = {
  id: string;                    // 예: `production:{orderId}:{revision}`
  companyId: CompanyId;
  source: { type: 'production' | 'production-reversal' | 'oem'; id: string };
  expectedOperationIds: string[];
  status: 'pending' | 'processing' | 'complete' | 'failed';
  lastError?: string;
  createdAt: string;
  completedAt?: string;
};
```

`status`만 믿지는 않는다. 완료 여부는 `expectedOperationIds`에 대응하는 실제 원장 문서가 모두
있는지로 다시 계산할 수 있어야 한다. 작업 문서는 재개 위치와 오류를 보여주는 표다.

주문 생산 순서는 다음과 같다.

1. 주문 상태와 수량에서 revision과 예상 원료 작업 ID를 정해 job을 만든다.
2. 원료별 `executeRawInventoryCommand`를 실행한다.
3. 이미 끝난 원료는 같은 작업 ID라 no-op으로 통과한다.
4. 전부 끝나면 결정적 ID로 생산기록과 품목 재고 증감을 적용한다.
5. 주문에 `rawInventoryJobId`와 소비 로트 스냅샷을 저장하고 job을 완료한다.

4~5단계가 실패해도 재실행 시 원료가 다시 빠지지 않는다. 생산기록과 품목 재고도 각각 주문+
revision 기반의 결정적 ID와 트랜잭션 증분을 써야 한다.

주문 수량을 바꿔 재처리할 때는 revision을 올린다. 이전 job의 원료 이벤트를 각각 reverse한
뒤 새 job을 적용한다.

## 9. 삭제는 역기록으로 바꾼다

- 원장 화면의 삭제 버튼은 `취소`로 바꾼다.
- 원본 이벤트는 그대로 두고 `reverse:{원본 operationId}`를 추가한다.
- 사용 취소는 원본 `lotChanges`에 적힌 로트로 정확히 복원한다.
- 입고 취소는 해당 입고 로트의 남은 양 안에서만 허용한다. 이미 소비된 양까지 지우지 않는다.
- 실사는 다음 실사와 후속 이동이 없을 때만 취소한다. 그 외에는 새 실사로 바로잡는다.
- 로트 자체도 hard delete하지 않고 소진 이벤트(`deplete-lot`)와 `voidedAt`을 남긴다.

### 같은 원본을 두 번 취소하지 못하게 한다 — `ReversalGuard`

원본 이력이 있다는 것만으로는 못 막는다. 취소 이력은 **원본과 다른 `operationId`** 로 만들어지므로,
id 가 다른 취소를 두 번 보내면 둘 다 통과해 **원본이 두 번 되돌아간다.**

```
reversalGuards/{원본 operationId}
```

원본당 문서 하나만 만든다. 취소 명령은 트랜잭션 안에서 이 문서를 **읽고, 없을 때만** 쓴다 —
상태·이력과 같은 트랜잭션이라 갈릴 수 없다. 이미 있으면 `rejected`(`ALREADY_REVERSED`)다.

취소한 업무를 **다시 하려면** 취소를 취소하는 게 아니라 **새 `operationId` 로 원본 명령을
다시 만든다.**

### 되돌리기는 상태가 아니라 이력을 근거로 한다

복원은 `lotChanges` 의 `lotSnapshot` 을 쓴다. 상태의 `recentDepletedLots` 는 40개까지만 들고
있어서, 오래 전에 소진된 로트를 그걸로 되살리려 하면 **못 찾는다.**

## 10. 실사와 소급 입력

실사는 transaction에서 상태를 목표량으로 맞추고 `targetKg` 이벤트를 함께 만든다. 상태 문서의
`stocktakeAnchor`(`effectiveAt` · `operationId` · `sequence`)도 같은 transaction에서 갱신한다.

마지막 실사보다 앞선 기록을 뒤늦게 넣으면 현재 상태를 다시 움직이지 않는다. 실제 원장
이벤트는 업무상 수량을 `reportedDeltaKg`에 남기고 `appliedDeltaKg: 0`,
`backdatedBeforeStocktake: true`, 빈 `lotChanges`를 저장한다. **이력은 적용된 것이므로
`revision`은 올라간다.** 현재 잔량은 `sequence` 순으로 `appliedDeltaKg`를 보며, 기간별
입고·사용 보고서는 `effectiveAt`과 `reportedDeltaKg`를 본다. 두 시간을 한 정렬로 해결하려
하지 않는다.

이 판정은 화면이 들고 있는 원장 배열이 아니라 transaction에서 읽은 상태의 실사 정보로 한다.

### 같은 시각에 실사와 입출고가 겹치면

`effectiveAt`만으로는 선후를 못 가린다 — 같은 날 실사를 찍고 그날 사용을 입력하는 일이 흔하다.
**앵커보다 앞이냐**는 이렇게 본다.

```
소급이다  ⇔  effectiveAt < stocktakeAnchor.effectiveAt
```

**같으면 소급이 아니다.** 실사와 같은 시각의 입출고는 실사 **뒤에** 일어난 것으로 보고 그대로
적용한다. 근거는 둘이다 —
· 실사는 "그 순간 창고에 이만큼"이고, 같은 시각의 사용은 그 뒤 일이라고 읽는 게 업무 감각에 맞다.
· 같으면 소급으로 치면, 실사 당일 입력한 사용이 **영영 재고에 안 잡힌다**(그날 것을 그날 넣는 게
  가장 흔한 입력인데 그게 통째로 무시된다).

정말 실사 이전 일이면 날짜를 하루 앞으로 적는다 — 그건 사람이 아는 사실이다.

## 11. 서류는 실제 재고가 끝난 뒤 계산한다

실제 재고와 서류 사이의 의존 방향은 한쪽뿐이다.

```text
실제 재고 코어 ───────┐
배송완료 판매자료 ─────┼─> 서류 계산기 ─> 화면·엑셀·PDF
rawDocEntries 손입력 ──┘

서류 계산기 ─X─> rawInventories / rawMaterialLedger
```

`rawDocEntries`에 실제 원장을 통째로 복사하지 않는다. 복사본을 저장하면 실제 원장 취소·정정 때
두 컬렉션이 다시 갈린다. `buildRawDocSheetFor()`가 조회 시 다음 세 입력을 합치는 것을 기본으로
한다.

| 입력 | 서류에서 쓰는 것 | 서류에서 쓰지 않는 것 |
|---|---|---|
| 실제 원장 movement | 서류 규칙상 인정되는 실제 입고와 그 취소 | 생산 자동차감, 실제 실사, 로트삭제 |
| 배송완료 판매자료 | `docSaleLines → docOilKg → addOilByRaw`로 되계산한 사용량 | 실제 생산 시점의 사용량 |
| `rawDocEntries` | 첫 달 전월이월, 서류 전용 실사·손조정 | 실제 원장 복사본 |

실제 입고를 서류 줄로 바꾸는 규칙은 `toRawDocumentReceipt(movement)` 한 함수에 둔다. 판정은
메모 문자열이나 원료명으로 하지 않고 `companyId`, `rawItemId`, `kind`, `source.type`을 사용한다.
서류 품목명으로 묶는 규칙은 품목 기준정보의 명시적 매핑을 쓰며, 이름이 같은 원료를 검색해
첫 항목을 고르지 않는다.

취소는 실제 원장의 원본과 `reverse` movement를 함께 읽어 서류 입고량도 상쇄한다. 서류 결과는
같은 입력과 같은 계산 버전이면 항상 같아야 한다. 계산 도중 실패하면 오류를 보여주고 다시
계산하면 되며, 이미 완료된 재고를 재실행하지 않는다.

조회량 때문에 나중에 서류 결과를 저장할 필요가 생겨도 그것은 재생성 가능한 캐시로만 둔다.
캐시 키는 `sourceOperationId + documentRuleVersion`으로 정하고, 캐시 저장 실패를 재고 실패로
취급하지 않는다. 현재 규모에서는 복사 컬렉션을 먼저 만들지 않고 조회 시 계산하는 편이 단순하다.

## 12. OEM·제품 로트를 실제 재고와 구분한다

기존 [OEM-임가공-설계.md](OEM-임가공-설계.md)의 품목별 실물 재고 결정을 따른다.

| 상황 | 실제 원료 원장 | 원료 상태 | 제품 재고·로트 | 서류용 수불부 |
|---|---|---|---|---|
| 우리 원료를 외주처로 보냄 | 사용 | 감소 | 없음 | 사용 |
| 외주 후 벌크로 돌아옴 | 입고 | 증가 | 없음 | 입고 |
| 완포장품으로 돌아옴 | 없음 | 변화 없음 | 증가 | 원료 환산 입고 |
| 임가공 완제품을 출고함 | 없음 | 변화 없음 | 감소 | 필요 시 원료 환산 사용 |

현재 `rawUsageLedgerOnly`와 `receivedByRaw`가 서류 수량을 만들려고 실제 원장에 쓰는 줄은 없앤다.
서류 사용량은 배송완료 판매자료에서 후처리하고, 완포장 입고는 제품 재고와 제품 로트에만
남긴다. 정말 서류 손입력이 필요한 예외만 `rawDocEntries`에 기록한다.

## 13. 실행 위치와 보안

첫 단계는 공용 TypeScript 서비스와 Firestore client transaction으로도 정합성을 확보할 수 있다.
하지만 현재 익명 인증과 전면 허용 rules에서는 옛 클라이언트나 임의 코드가 공용 함수를 건너뛸
수 있다.

최종 단계에서는 `executeRawInventoryCommand`를 callable Cloud Function으로 옮기고 다음을
서버에서 검증한다.

- Firebase Auth UID와 직원·회사·권한
- 명령의 회사와 원료 상태 문서 회사 일치
- operation ID와 업무 원본의 소유 관계
- 허용 수량과 명령 종류

Firestore rules는 클라이언트의 `rawInventories`·`rawMaterialLedger` 직접 쓰기를 막고 읽기만
역할별로 허용한다. 함수 전환은 인증 개편과 함께 진행하며 `functions`는 별도 배포라는 점을
배포 절차에 넣는다.

## 14. 대조와 관측

대조 결과는 조회 실패를 정상으로 취급하지 않는다.

```ts
type LedgerLotCheck =
  | { status: 'ok'; ledgerKg: number; stockKg: number; lotKg: number }
  | { status: 'gap'; ledgerKg: number; stockKg: number; lotKg: number; gaps: number[] }
  | { status: 'error'; message: string };
```

- 조회는 원료명이 아니라 `companyId + rawItemId`로 한다.
- job이 일정 시간 `processing`이면 관리자 화면에 남긴다.
- 명령 실패와 대조 실패는 성공 토스트로 덮지 않는다.
- 알림 저장 실패가 본 재고 transaction을 실패시키지 않도록 알림은 커밋 뒤 별도로 보낸다.
- 서류 계산 실패와 누락은 재고 불일치와 별도 상태로 표시한다. 서류 오류를 고치면서 재고를
  보정하지 않는다.
- 대조기는 안전망이며 실제 정합성은 transaction과 operation ID가 지킨다.

## 15. 이관 순서

1. `scripts/diag-raw-ledger-lots.mts`로 회사·원료별
   `원장잔량 / 벌크로트 / 제품로트 / items.stock / 회사·rawItemId 없는 줄 / 마지막 실사 /
   상태 문서 크기`를 JSON으로 조사한다. 읽기 전용 조사 뒤 스크립트는 지운다.
2. `RawInventoryState`, `RawInventoryMovement`, `RawInventoryJob` 타입과 순수 로트 계산을 만든다.
3. 에뮬레이터 시험을 먼저 만든 뒤 `executeRawInventoryCommand` client transaction을 구현한다.
4. 기존 `items.stock/lots`에서 `rawInventories` 초기 문서를 만드는 이관 스크립트를
   dry/apply/undo·백업 JSON과 함께 실행한다.
5. 기초이월 → 손입력 → 매입입고 → 조정·실사 → 생산·취소 → OEM의 **실물 변화** 순으로
   호출부를 교체한다.
6. `buildRawDocSheetFor`의 실제 입고 입력을 새 movement 구조에 연결하고, 서류를 위해 실제 원장에
   쓰던 OEM·판매 파생 줄을 제거한다.
7. 관리자 앱과 직원 앱을 같은 시점에 배포하고 새 쓰기만 공용 명령으로 받는다.
8. 배선 시험으로 서비스 밖의 `rawMaterialLedger`·`rawInventories` 수량 쓰기를 금지한다.
9. 옛 원장에 `companyId`와 `rawItemId`를 채우고, 실제 차이는 원장·실물 확인 후 보정한다.
10. 안정화 뒤 원료의 `items.stock/lots`, `lotsAreTotal`, 직접쓰기와 hard delete를 제거한다.
11. 인증 개편 뒤 callable Function과 rules로 쓰기 경계를 서버에 세운다.

DB 변경과 되돌리는 법은 단계마다 [DB-CHANGELOG.md](../DB-CHANGELOG.md)에 남긴다. 어느 쪽
숫자가 맞는지 코드가 추측해 자동 보정하지 않는다.

## 16. 반드시 잠글 시험

- 입고·사용·실사·로트삭제에서 상태와 원장이 한 transaction으로 함께 성공한다.
- transaction이 실패하면 둘 다 그대로다.
- 같은 operation ID를 두 번·동시에 보내도 수량은 한 번만 움직인다(`duplicate`).
- **같은 operation ID인데 명령 내용이 다르면 `conflict`로 막고 수량은 안 움직인다.**
- **문서 ID가 겹치지 않는다** — `po1/x`와 `po1_x`, 아주 긴 두 작업 ID가 다른 문서가 된다.
- **같은 원본을 두 번 취소하지 못한다** — 서로 다른 취소 ID로 보내도 두 번째는 거절된다.
- **40개보다 오래 전에 소진된 로트도 되돌리기로 정확히 되살아난다.**
- `revision`은 `applied`에서만 오르고 `duplicate`·`conflict`·`rejected`에서는 안 오른다.
  수량이 0인 소급 입력에서는 오른다. 언제나 `revision === 최신 sequence`.
- 실사와 **같은 시각**의 입출고는 소급이 아니라 그대로 적용된다.
- 같은 원료의 동시 입고와 사용이 직렬화되고 FIFO 결과가 맞는다.
- 주문 저장이 원료 처리 뒤 실패해도 재시도 시 이중 차감되지 않는다.
- job이 일부 원료 처리 뒤 실패하면 나머지만 이어서 처리한다.
- 생산 취소 재시도에서 이중 복원되지 않는다.
- 같은 이름의 태백·풍회 원료가 서로 영향을 주지 않는다.
- 원장 취소가 원본을 보존하고 실제 로트 분배대로 되돌린다.
- 실사 전 소급 입력이 현재 상태를 움직이지 않고 잔량도 바꾸지 않는다.
- OEM 완포장 흐름은 실제 원료 원장에 들어가지 않는다.
- 실제 입고만 서류 후처리 입력에 포함되고 자동차감·실제 실사·로트삭제는 제외된다.
- 배송완료 판매자료의 사용량과 서류 손입력이 실제 재고를 움직이지 않는다.
- 서류 계산이 실패하거나 같은 입력을 여러 번 계산해도 실제 재고와 실제 원장은 바뀌지 않는다.
- 실제 입고 취소가 서류 입고도 한 번만 상쇄하며 원본 이력은 남는다.
- 정상·불일치·조회실패가 서로 다른 결과로 나온다.
- 공용 서비스 밖의 원료 상태·실제 원장 수량 쓰기가 0건이다.

시험을 만든 뒤 공용 명령에서 원장 쓰기와 중복 방지 판정을 각각 일부러 빼서 시험이 실패하는지
확인한다. 둘 중 하나를 잡지 못하면 그 시험은 정합성을 지키지 못한다.
