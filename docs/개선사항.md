## 종합 평가 (구조 / 최적화 / 업무 구현)

### A. 구조 체계성 — ★★★☆☆ (보통)
- **좋은 점**: 공통 컴포넌트(PageHeader)·공통 서비스(firebaseService)·공통 유틸(lotUtils/rawReceipt/formula) 분리, 구독 중앙화(useAppData), 타입 단일 파일(types.ts), feature 폴더 구조.
- **문제 점**:
  - **God component**: `HaccpChecklist 4114줄`, `AdminApp 4039줄`, `TradeStatement 3693줄`, `ItemList 2419줄`. 한 파일에 상태·핸들러·렌더·비즈니스 로직이 다 몰림 → 유지보수·리뷰·재사용 어려움.
  - **비즈니스 로직이 UI 컴포넌트 안에**: 재고 차감·전표·입고 로직이 AdminApp render 클로저에 흩어짐(도메인 계층 부재).
  - **다중 진실 소스**: item.stock↔lots, PRODUCT_FORMULA↔item_formula, Standard_Price↔price 등.
  - **deprecated 이중 스키마 다수**(types.ts) → 곳곳에서 하위호환 분기.
  - **테스트 0개**(프로젝트 코드). 재고/원가 같은 정합성 핵심 로직에 회귀 방지 장치 없음.

### B. 최적화(읽기/성능) — ★★★★☆ (양호)
- **좋은 점**: 고volume 컬렉션(수불부·전표·채팅·반품·스냅샷 로그)은 **최근 7일 구독**, 과거는 온디맨드 로드 → 읽기 비용 통제 잘 됨. lot FIFO·수율 계산 등 도메인 연산 정돈됨.
- **문제 점**:
  - `purchaseOrders`·`items` **전체 라이브 구독** → 누적 시 매 세션 전량 읽기(#9). 특히 items는 `lots` 배열로 페이로드 큼.
  - **native alert/confirm 100곳** — 블로킹·비일관 UX(최적화된 인앱 모달/토스트 아님).
  - 일부 대형 리스트 페이지네이션 미흡(생산실적은 오늘 추가).

### C. 실제 업무 구현 — ★★★★☆ (넓게 구현, 제조 정합성 일부 미흡)
- **좋은 점**: 원료 입고/사용/lot·매출/매입 전표·세금계산서·배송·재고·생산실적·HACCP·인사까지 **업무 범위 매우 넓음**. 참기름 제조업 특유의 **원료 배합(BOM)·FIFO 차감·수불부**가 실제 워크플로우로 반영됨.
- **미흡한 점 (제조 정합성)**:
  - **생산 = 배송완료 가정** → 실제 제조공정/선제조(make-to-stock) 미반영(#4).
  - **반제품(wip) 원료 차감 없음**(#6).
  - **lot 역추적(리콜) 미구현**(#5), **실사조정이 lot 이력 뭉갬**(#3).
  - **월별 품목 재고 스냅샷 없음** → 정확한 월 손익 산출 어려움(#10).
  - OEM(완사입/임가공)·박스/낱개 variant 재고 미구현.

**한 줄 총평**: *업무 커버리지와 읽기 최적화는 양호. 다만 (1) 초대형 컴포넌트·다중 진실 소스로 구조 유지보수성이 약하고, (2) 제조·추적(선제조/반제품/역추적/실사이력) 쪽 정합성에 구멍이 있어, 이 두 축을 보강하면 완성도가 크게 오름.*

## 🔴 높음 — 데이터 정합성 / 리스크

### 1. 로트(lot) 무한 증가 → 문서 비대화
- **문제**: 소진된 lot을 삭제하지 않고 `status: 'depleted'`로 계속 보존. 원료 재고는 `item.lots` **배열 필드**(items 컬렉션)에 저장되므로, 몇 달 쌓이면 배열이 수백~수천 개.
- **영향**: 품목을 읽을 때마다 죽은 lot까지 통째로 로드(읽기 비용·속도), 장기적으로 Firestore 문서 1MiB 한도.
- **위치**: `deductFromLots`(`src/shared/lotUtils.ts`)에서 `status='depleted'` 처리, lots는 `item.lots`.
- **방향**: 소진 lot **주기적 정리**(N개월 지난 depleted lot 아카이브/삭제), 또는 서브컬렉션 `items/{id}/lots/{lotId}`로 이전.

### 2. 재고 단일 소스(single source of truth) 미완
- **문제**: 화면이 `item.stock`(로트 합계의 **미러**)을 읽음. 쓰기 경로는 lot 경유로 정리했지만, 어디서든 stock을 직접 수정하면 다시 lots와 어긋남.
- **영향**: 깨분참기름 같은 "수불부/lots는 맞는데 화면은 0" 불일치 재발 가능.
- **위치**: `components/ItemList.tsx` 원료 표시 `effStock = ... : product.stock` (약 989~999행). `lotStockInUnit(lots, material)`로 대체 가능.
- **방향**: **원료(raw)는 화면도 `lots` 합계를 직접 읽게** → stock 필드가 뭐든 무관, lots가 유일 기준.

### 3. 실사조정이 lot 이력을 뭉갬
- **문제**: 재고 실사정정 시 기존 입고 lot들을 '실사조정' lot으로 대체 → 이전 **공급처·입고일** 추적이 끊김. (2026-07-02 실사 리셋 때도 발생, 이전 입고 lot 추적 단절)
- **영향**: 리콜/추적 시 실사 이전 원료 출처를 못 따라감.
- **위치**: `commitStockEdit`(ItemList) / `adjustRawLots`(`src/shared/rawReceipt.ts`).
- **방향**: 실사는 기존 lot **유지 + 차액 조정 lot만** 추가(음수면 FIFO 차감)하여 출처 lot 보존.

### 4. 생산 = 배송완료 가정 (선제조 미반영)
- **문제**: 원료 차감·생산기록이 주문 **"배송완료(DELIVERED)"** 시점에만 생성. 미리 만들어 재고로 쌓는 **선제조(make-to-stock)** 는 시스템에 안 잡힘.
- **위치**: 트리거 = `onUpdateStatus(id, DELIVERED)` → `deductSubmaterialsForOrder` (`AdminApp.tsx` 약 1347행).
- **방향**: 실제 "제조 공정" 기록(투입 원료 → 완제품 lot)을 주문과 분리. 메모의 `BOM 출고 차감 설계`(선제조형 vs Phantom/Kit) 미결과 연결.

## 🟡 중간 — 완성도

### 5. 역추적(lot → 제품, 리콜) 미구현
- 정방향(제품 → 투입 원료 lot)만 구현됨(`order.rawConsumedLots`). "이 lot이 들어간 제품 전부"는 아직 못 뽑음.
- **방향**: 소비 시 `consumedLotIds: [lotId,...]`(array-contains 조회용)도 저장 → lot 선택 시 소비 주문/제품 목록 조회.

### 6. 반제품(wip) 원료 차감 없음
- 차감이 `category === 'product'`(완제품)만 대상. 반제품 제조 시 원료 소비가 추적에서 누락.
- **위치**: `deductSubmaterialsForOrder` 약 735행 `if (product.category !== 'product' ...) continue`.

### 7. BOM 이중 소스
- `PRODUCT_FORMULA`(코드 하드코딩, `src/constants/formula.ts`) + `item_formula`(Firestore) 둘 다 존재. 우선순위는 item_formula.
- **위치**: `AdminApp.tsx` 약 766~772행.
- **방향**: **item_formula 단일화** (코드는 시딩/문서용으로만) → 드리프트 방지.

### 8. 단일/다품목 발주카드 혼재
- 발주카드가 단일품목(`itemId`)과 다품목(`items[]`) 두 형태. 재고현황 "발주내역 입고대기"는 `productMap.get(conf.id)`로 렌더 → **다품목 PO는 안 그려짐**.
- **위치**: `ItemList.tsx` — 입고/반품 탭 섹션(약 780행, poLines 기반, 정상)과 재고현황 섹션(약 1598행, 단일품목 전용).
- **방향**: 발주카드 렌더를 `poLines(po)` 기반으로 통일.

### 9. purchaseOrders / items 전체 라이브 구독 (읽기 비용 누적)
- `useAppData`에서 `purchaseOrders`·`items`·`partners`·`inventorySnapshots`·`adjustmentRequests` 등을 **전체(full) `onSnapshot`** 로 구독. (`src/shared/hooks/useAppData.ts` 157~191행)
- **문제**: `purchaseOrders`는 발주/매입전표마다 쌓여 시간이 지나면 수천 건 → **매 세션 전량 읽기**. `items`도 각 문서에 `lots` 배열이 붙어 페이로드가 큼(#1과 연결).
- **방향**: `purchaseOrders`는 **상태/기간 제한 구독**(예: `status != 'received'` 또는 최근 N개월). 나머지 고volume도 recent 구독 검토. (수불부/전표/채팅 등은 이미 최근 7일 구독으로 잘 돼 있음)

### 10. inventorySnapshots가 총액만 저장 (품목별 없음)
- 재고 마감 스냅샷이 `{ yearMonth, recordedAt, value(총액) }` 만 저장 → **품목별 재고 스냅샷 없음**.
- **문제**: 월별 상세 손익·재고 분석 불가. 총액도 lots 미반영분(예: 깨분참기름) 있으면 과소 계상.
- **방향**: 마감 시 **품목별 수량·평가액 스냅샷** 저장.

## 🔵 구조 / 기술부채 (리팩터링)

### 11. God component 분해
- `HaccpChecklist(4114)`·`AdminApp(4039)`·`TradeStatement(3693)`·`ItemList(2419)` 등 초대형. 한 파일에 상태+핸들러+렌더+로직이 몰림.
- **방향**: 뷰/핸들러/도메인 로직 분리. AdminApp의 핸들러(재고·전표·입고)를 **도메인 서비스/훅**으로 추출.

### 12. 도메인 계층 부재
- 재고 차감·전표·입고·원가 동기화가 UI 컴포넌트 render 클로저에 흩어짐 → 같은 규칙이 여러 곳에서 다르게 구현되어 버그(오늘의 재고 불일치·비대칭 입고 등).
- **방향**: `inventory`/`ledger` 같은 **순수 도메인 모듈**로 규칙 단일화(#13과 연결).

### 13. 재고 변경 로직 분산
- 오늘 5+ 경로를 lot 경유로 고쳤으나(재고조정·반품·정정·행수정·전표입고 제거), 재고 변경 진입점이 여전히 여러 곳.
- **방향**: 원료 재고 변경을 **단일 헬퍼**(`adjustRawLots`/`recordRawMaterialReceipt`)로 강제.

### 14. 테스트 0
- 프로젝트 코드에 단위/통합 테스트 없음. 재고·원가·lot·수불부 같은 정합성 핵심에 회귀 방지 장치 부재.
- **방향**: 최소한 `lotUtils`(FIFO/혼합/차감)·`formula`(kg 환산/배합)·`rawReceipt` 순수 함수에 단위 테스트.

### 15. deprecated 이중 스키마 정리
- `types.ts`에 `Standard_Price/price`, `itemType/category`, `partnerId/partnerIds`, `boxSize/defaultBoxConfig`, `spec/용량` 등 하위호환 필드 다수 → 코드 곳곳 분기.
- **방향**: 마이그레이션 마무리 후 deprecated 제거, `as any`(54곳) 축소.
