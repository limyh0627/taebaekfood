# OEM(임가공) 재고·전표 설계

> 작성: 2026-07-17 · 상태: **설계 확정, 미구현**
> 목적: 우리 원료를 외주공장에 보내 가공받아 완제품으로 돌려받는 흐름(임가공/OEM)을 재고·전표에 반영.
> **착수는 볶음참깨 완사입 모델이 안정화된 뒤.** 지금 구현하지 말 것.

---

## 0. 완사입 vs OEM — 한 줄 요약

| | 완사입 | OEM(임가공) |
|---|---|---|
| 뭘 사나 | 남의 **완제품**을 사옴 | 남한테 **가공만** 시킴 (가공비만 지급) |
| 원료 | 무관 | **우리 것** — 우리가 보냄 |
| 원료수불부 | 안 잡힘 | 참깨 매입~소진까지 다 잡힘 |
| `procureType` | `'완사입'` | `'임가공'` |

핵심 통찰: **OEM은 판매 시점이 아니라 조달 시점에서만 자체생산과 다르다.**
판매할 때 OEM 완제품은 완사입처럼 자기 재고만 −N (생산처리 없음). 원료는 이미 가공입고 때 소진됐다.

---

## 1. 재고 모델 — 외주재고 분리 (재공품)

참깨를 외주공장에 보내도 **소유권은 우리 것**이다. 남에게 판 게 아니라 우리 물건을 맡긴 것.
그래서 장부에서 없애지 않고 **참깨(외주)** 라는 재고 칸으로 옮긴다. 총 재산이 연속으로 유지돼
월말 재고자산이 정확해진다 (복식부기·재무상태표 방향과 맞음).

```
① 참깨 5T 매입        참깨(본) +5T                      · 수불부 입고 · 매입전표(참깨값)
② 1T 외주 발주        참깨(본) −1T, 참깨(외주) +1T       · 전표 없음 (우리 것의 이동)
③ 가공입고 950kg      참깨(외주) −1T, 볶음참깨 +950kg     · 로스 50kg 자동 · 가공비 전표
④ 판매                각 완제품 −N                       · 매출전표 (완사입처럼)
```

**전표는 ①(참깨 매입)과 ③(가공비) 딱 2장.** ②·④엔 OEM 관련 전표 없음(④는 일반 매출).

### 로스는 자동
보낸 참깨(1000kg)와 받은 볶음참깨(950kg)의 차이 50kg = 수율손실. **입력하지 않는다.**
③에서 받은 것(950kg)만 입력하면, 배치가 보낸 양(1000kg)을 알고 있으므로 로스가 저절로 나온다.

## 2. 발주카드(PurchaseOrder) 재활용

OEM 배치 = 발주카드의 한 종류다. 발주카드의 `pending → received` 흐름이 OEM의 "나감 → 돌아옴"과
같은 골격이라, 새 컬렉션을 만들지 않고 `PurchaseOrder`에 필드만 얹는다.

```ts
// PurchaseOrder에 추가
poType?: 'oem';                              // 일반 발주 vs OEM
oemPartnerId?: string;                       // 외주공장
oemSent?: { material: string; kg: number };  // 내보낸 원료 (배치 열 때 기록, 로스 계산 기준)
// status: 'sent' | 'received' 로 OEM 상태 표현 (기존 pending/received 재사용 or 확장)
// items[]  : 돌아온 완제품/벌크 여러 규격 (기존 멀티품목 구조 그대로)
// linkedStatementId : 가공비 전표 연결 (기존 필드 그대로)
```

### 발주카드 재활용으로 공짜로 딸려오는 것
- **부분 입고** — 1000kg 보내고 500 받고 450 받고. 발주카드가 이미 멀티품목·부분처리 지원.
- **외주재고 현황** — `poType:'oem' && status:'sent'` 카드 목록 = 지금 외주 나가 있는 것. 별도 화면 불필요.
- **가공비 전표 연결** — `linkedStatementId` 그대로.
- **입고 UI** — `ReceivingReturnsManager` 선입고·스캔입고 화면 재사용.

## 3. 처리 흐름

### ② OEM 발주 (원료 내보냄)
일반 발주는 "받을 물건"을 적지만, OEM은 **"보낼 원료"**를 적는다. 발주하는 순간 참깨가 실제로
나가므로, 카드 생성과 동시에 재고가 이동한다 (일반 발주는 카드 생성 시 재고 불변).

```
OEM 발주 [외주공장]  참깨 1000kg  →  [발주]
  → adjustRawLots(참깨,      -1000)   // 본재고 FIFO 차감 + 수불부 출고
  → adjustRawLots(참깨-외주, +1000)   // 외주재고로 이동
  → PurchaseOrder { poType:'oem', oemSent:{참깨,1000}, status:'sent', items:[] }
```

`adjustRawLots`(`src/shared/rawReceipt.ts`)가 음수 delta로 FIFO 로트 차감 + 수불부 기록을 이미 한다. **재사용.**

발주 트리거 2경로:
- **수동** — "볶음참깨 떨어졌으니 외주 돌리자" → 참깨 kg 직접 입력 (주 사용)
- **자동 알림** — 볶음참깨 부족 알림이 뜨면 소요 참깨량을 `buildFormula`로 역산해 안내
  (완제품 부족 → 원료 소요 변환은 기존 부족체크 로직 재사용)

### ③ 가공입고 (완제품 돌아옴) — 하이브리드
돌아오는 형태가 두 갈래. 입고 줄에서 고른 대상 품목이 완제품이냐 raw냐로 자동 구분.

```
가공입고 [OEM카드 선택]  [일자]
 돌아온 것            도착형태      재고 반영
 볶음참깨/10kg박스  20  완제품   →  10kg박스 +20
 볶음참깨/20kg박스  10  완제품   →  20kg박스 +10
 볶음참깨/낱개1kg    5  완제품   →  낱개 +5
 볶음참깨 20kg자루   N  벌크    →  raw-볶음참깨 +(N×20)kg
 ────────────────────────────────────────────
 받은 총 볶음참깨 = 합계 kg
   → 참깨(외주) −(배치 oemSent.kg)      // 배치 닫힘
   → 로스 = oemSent.kg − 받은합계kg     // 자동
   → 가공비 = 받은합계kg × kg단가 → 매입전표 1장 (외주공장, 계정 '외주가공비')
   → PurchaseOrder.status = 'received', linkedStatementId = 가공비전표
```

- **박스·낱개** = 각각 독립 완제품. `procureType:'임가공'`. 판매 시 완사입처럼 자기재고 −N.
- **20kg 자루** = 벌크(raw-볶음참깨)로 흡수. 여기서 80g/140g/200g/350g/500g 소분이 차감(기존 formula).
- 같은 20kg라도 "박스"(팔 완제품)와 "자루"(소분용 벌크)는 다른 품목.

## 4. 새로 필요한 것 (요약)

| 대상 | 추가 |
|---|---|
| `Item` | `procureType: '완사입' \| '임가공'` (확장). OEM 완제품은 판매 시 `isGoodsItem` 취급 |
| `Item` (또는 별도) | **참깨(외주)** 재고 홀더 — 가장 단순: 원료마다 병렬 raw 품목 1개 |
| `PurchaseOrder` | `poType`, `oemPartnerId`, `oemSent`, status 'sent' 확장 |
| `AccountCode` | **외주가공비** 신설 (제조원가) |
| 화면 | OEM 발주 모드(내보낼 원료 입력), 가공입고(하이브리드 여러 줄) |
| 로직 | 발주 시 본→외주 이동, 가공입고 시 외주정리+완제품/벌크입고+로스+가공비 |

### 재사용하는 것 (안 만들어도 됨)
- `adjustRawLots` — 본→외주 이동, FIFO 차감, 수불부
- `PurchaseOrder` status/`linkedStatementId`/`items[]` — 배치·상태·부분입고·전표연결
- `buildFormula` — 완제품 부족 → 원료 소요 역산
- `ReceivingReturnsManager` — 입고 UI
- 매입전표 생성 — 가공비 전표

| 항목 | 결정 |

| 소분 80g~500g | 벌크에서 (기존 formula) |
| 부분 입고 | 발주카드 멀티품목으로 지원 |

## 5-1. 추가 확정 (2026-07-17, 리스크 문답)

| 항목 | 결정 | 설계 영향 |
|---|---|---|
| **로트 추적** | **유지** — 어느 공급사 참깨였는지 볶음참깨까지 이어감 | 참깨(외주)를 kg만이 아니라 **로트째** 보관. 자체생산의 `rawConsumedLots`처럼 OEM 배치에도 소비 로트 스냅샷을 남긴다. 병렬 raw 품목 방식이면 로트 이동으로 처리. HACCP·회수 역추적 가능. |
| **참깨 반납** | **없음** — 전량 볶아 볶음참깨로만 돌아옴 | 로스 = `보낸참깨 − 받은볶음참깨` 단순 성립. 가공입고에 '참깨 반납' 줄 불필요. |
| **가공비 부가세** | **과세** (세금계산서 수취) | 가공비 매입전표를 **공급가 + 세액(10%) 분리**로 기록. 매입세액공제 대상. (대체전표는 부가세 없었지만 가공비는 진짜 세금계산서 거래라 다르다.) |
| **배치 원료 종류** | 지금은 참깨 1종, 그러나 **여러 종 가능하게 일반화** | `oemSent`를 **배열**로: `oemSent?: { material: string; kg: number }[]`. 로스도 원료별로 계산. 지금은 1원소만 쓰지만 구조는 다종 대응. |

## 5-2. 박스·낱개·소분 재고와 종합 (2026-07-17 확정)

볶음참깨 계열(박스/낱개/소분)의 재고를 어떻게 묶을지 결정.

**결정: A안 — 재고는 품목별 실물, 종합은 서류에서만.**

```
재고(운영)  10kg박스·20kg박스·낱개1kg·소분 = 각자 실물 재고. 지금 그대로. unpackTo 개봉버튼 유지.
서류(집계)  원료수불부 등에서만 spec kg × 재고수량으로 그룹 종합 (나중에 세팅)
```

- **계층(item_bom) 정식화 불필요.** 종합은 `품목` 필드(공통값 "시골향볶음참깨")를 그룹키로,
  `spec`("10kg"/"1kg")을 kg 환산 기준(`parsePackageKg`)으로 쓰면 된다. 데이터가 이미 다 있음.
- **phantom(무재고 전개) 안 씀.** 박스는 실물 재고를 든다(창고에 미리 포장해 쌓아둠).
- 이전 미결이던 "완사입 박스 ↔ 벌크 연결"은 이 결정으로 닫힘 — 재고에선 안 잇고, **서류에서만** 합산.

### 서류 종합 시 주의
- **`볶음참깨(벌크)/20kg`(p-1779937553909)는 종합에서 제외하거나 별도 취급.** 얜 `rawMaterialName:볶음참깨`라
  입고 시 raw-볶음참깨 벌크(kg)로 **직접** 들어간다. 완사입 박스(판매용)와 성격이 다르다.
  **이 품목은 삭제 검토 중(사용자 미결)** — 존치 여부 정해지면 종합 규칙 확정.
- 이름 비슷한 `볶음참깨/20kg박스`(완사입 판매용, p-1780625559322)와 위 벌크(p-1779937553909) 혼동 주의.

## 6. 미결 / 나중에 정할 것
- **참깨(외주) 홀더 구현 방식** — 병렬 raw 품목(단순) vs 로트에 location 태그(정교).
  **로트 추적 유지가 확정됐으므로**, 병렬 품목이어도 로트를 들고 가야 한다. location 태그가
  로트 정체성 보존엔 더 자연스러우나 로트 시스템 개편이 필요 → 착수 시 재검토.
- **가공비 단가 관리** — 외주공장별 kg단가를 partner_item 같은 데 저장할지, 입고 때 직접 입력할지.
- **`볶음참깨(벌크)/20kg` 품목 존치 여부** — 사용자 삭제 검토 중. 결정 후 서류 종합 규칙 확정.

## 7. 왜 지금 하지 않는가
- 볶음참깨 **완사입** 모델이 2026-07-14에 막 배포돼 검증 전. OEM은 그 위에 얹는 것이라 완사입이
  안정된 뒤 착수해야 안전하다.
- 현재 완사입으로 잡힌 10kg/20kg 박스 중 일부는 실제로 OEM 산출물일 수 있다. 구현 착수 시
  **어느 품목이 완사입이고 어느 게 OEM인지** 먼저 확정해야 한다(원료를 우리가 보내면 OEM).
