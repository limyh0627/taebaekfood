# 거래처·배송지 기본 배송방식

## 요청과 적용 범위

거래처 관리에서 배송·화물·수령·택배 중 기본 배송방식을 정한다. 여러 배송지를 사용하는 거래처는 배송지마다 따로 정한다. 신규 매출처와 매출·매입 겸용 거래처는 빈 선택으로 시작하고 직접 선택해야 등록된다. 금융기관과 매입전용 거래처에는 무관한 배송 선택을 강제하지 않는다.

`Partner.defaultShipMethod`와 `ShipTo.defaultShipMethod`를 추가한다. 주문 기본값은 유효한 선택 배송지 설정, 거래처 설정, 기존 판매 채널 기본값 순서다. 기존 미설정 거래처의 주문을 새로 막지 않는다. 기존 주문 자체의 배송방식은 변경하지 않는다. 판매 채널과 배송방식을 구분하며 주문 문장에서 배송방식을 AI로 추출하지 않는다.

주문에서 직접 바꾼 값은 같은 거래처 자료가 갱신되어도 유지한다. 사용자가 거래처나 배송지를 명시적으로 바꾸면 그 대상의 기본값으로 시작한다. 신규 배송지는 방식을 선택하여 추가하고 기존 미설정 배송지는 설정 상태를 표시한다.

## 한 번 적용할 이관 준비

화면의 제한된 주문 목록 대신 전체 주문을 읽는 별도 도구를 준비한다. 회사·거래처·정확한 배송지 ID로 나누고 이미 존재하는 기본값은 덮어쓰지 않는다. 배송지 없는 주문을 임의의 배송지에 연결하지 않는다. 보관·삭제 배송지와 의미가 불확실한 자료는 보류한다.

후보 기준은 최근 주문일에 명시되어 있는 배송방식이다. `createdAt`은 직접 작성 주문에서는 사용자가 고른 주문일이므로 실제 입력 시각이나 실제 출고 시각이라고 설명하지 않는다. 같은 최신 주문일에 서로 다른 방식이 있거나 최신 기록의 방식이 비어 있으면 오래된 값으로 대신 채우지 않는다. 채널에서 추정한 기본값을 실제 배송 기록으로 이관하지 않는다.

실제 운영 적용 전 후보·보류 건수와 기준을 확인한다. 원문 백업·계획 해시·문서 버전 조건을 준비하고, 승인한 정확 범위만 적용한다. 되돌리기도 적용 영수증과 현재 버전이 맞을 때만 수행한다. 도구 준비만으로 적용 완료를 의미하지 않으며 실제 적용 결과는 아래 마감 기록으로 구분한다.

## 검증과 배포

앱 관련 고유 9파일 109개 시험이 통과했다(공용 34개, 화면 및 기존 AI 보호 75개). 배송지 우선순위·직접 선택 보존·필수 선택·Enter 우회 방지의 보호 조건을 제거한 변이가 실제 실패하는 것을 확인하고 복원했다. 전체 수천 개 시험은 반복하지 않았다.

별도 이관 도구는 합성 39개와 실제 localhost Firestore REST 1개가 통과했다. 실제 REST는 쓰기 요청의 원자 적용·버전 충돌·조건부 되돌리기를 검증했고 자기 시험 문서만 정리했다. CLI 전체 실행은 합성 시험 근거와 구분한다. 독립 검수에서 원문 복제 중 특수 숫자 손실 가능성을 발견해 해당 원문을 백업 생성 전에 거절하도록 보완했다.

실제 컴포넌트의 합성 화면에서 신규 등록의 빈 필수 선택·선택값 저장, 배송지별 수정, 직접·복사 주문의 기본값과 수동 변경값 저장을 확인했다. 복사 주문 합성 fixture의 필수 `palletStocks` 누락으로 생긴 검수 화면 오류는 fixture를 보완한 뒤 분석·저장을 재확인했다. 운영 결함으로 집계하지 않는다. 모바일에서 배송방식 선택란 때문에 이름 폭이 좁아진 배치는 이름과 방식의 줄을 분리해 수정했고 최종 390px 검수에서 가로 넘침 없이 저장을 확인했다.

모바일 보완 후 앱 전체 타입 검사와 양 앱 빌드가 종료 0이다. 관리자 16.79초·직원 14.81초, 양 PWA 생성 및 제품 15파일의 빌드 전후 SHA 일치, 산출물 148개 해시와 FCM 원본 복원을 확인했다. 보완 전 근거는 그대로 두고 별도 최종 근거에 기록했다. 사전 생성과 검사도 종료 0(91컬렉션·739필드·491소스)이며 앱 15파일·이관 2파일·계획의 독립 검수는 CLEAR다. 실제 배포와 운영 이관은 아래 별도 마감 기록을 따른다.

## 운영 읽기 결과와 승인 적용

전체 거래처 349개·주문 566개를 읽은 계획은 변경 101문서, 거래처 기본값 100개·배송지 기본값 1개다. 모두 태백이며 풍회 후보는 없다. 이력 없는 범위 118개, 최신 방식이 비어 있는 범위 72개, 최신 주문일 방식 충돌 1개는 채우지 않는다. 집계는 범위별 수치이므로 거래처 건수와 단순 합산하지 않는다. 보수적으로 제외한 표식이 실제 삭제 확정이라는 뜻은 아니다.

계획 해시는 `84edbc7ba9b578730590537775b63e9c1d9942160e34a601e002003af67672a5`다. 별도 담당이 로컬 백업의 원문·버전·허용 변경 필드·계획 재계산·타필드 보존을 확인했다. 전체 조회는 원자 스냅샷이 아니다. 사용자 “해당 101개 기본값 적용 허용” 답변 후 원문과 버전을 다시 대조해 단일 원자 commit으로 101문서를 적용했다. 종료 0·쓰기 101이다. 독립 사후 GET에서 현재 전체 원문과 계획 after, 실제 영수증의 나노초 버전이 101개 모두 일치했고 다른 필드는 보존됐다. lock·실패 파일은 없으며 undo는 실행하지 않았다. 자세한 적용·복원 경계는 [DB 변경 기록](../DB-CHANGELOG.md)을 따른다. 비공개 백업과 실제 거래처·주문 원문은 Git에 포함하지 않는다.

## 관리 저장과 실패 복구 후속

기본 배송방식은 거래처 관리에서 사용자가 직접 변경하여 저장할 때만 갱신한다. 주문의 배송지나 배송방식을 바꿨다는 이유로 관리 기본값을 자동 학습하거나 저장하지 않는다. 위 101개 이관은 승인한 한 번의 적용이다.

신규 등록과 기존 수정은 실제 저장 응답을 기다린 뒤 닫는다. 연결·권한 오류가 나면 입력과 배송 설정을 유지하고 원인과 다시 시도하는 방법을 안내한다. 대기 중에는 중복 제출과 다른 폼 전환을 막고, 닫힌 폼의 늦은 응답이나 주소검색 결과가 새 폼에 적용되지 않도록 한다. 회사 전환은 관리 화면을 새로 구성한다.

신규 등록은 같은 폼에서 등록 번호를 유지한다. 등록 전용 트랜잭션은 없는 문서만 만들며, 같은 회사의 요청 내용이 이미 저장됐다면 추가 쓰기 없이 성공한다. 요청 내용과 다른 기존 문서는 덮어쓰지 않고, 사용자가 명시적으로 ‘기존 거래처 확인/수정’을 눌렀을 때 현재 자료를 연다. 다른 회사 자료는 오류에 노출하지 않는다. 일반 추가·수정 호출과 주문 배송지 선택 정책은 변경하지 않는다.

집중 시험은 서비스·연결·실제 로컬 SDK 및 관련 기존 시험 74개와 UI 22개가 통과했다. 보호조건 변이가 실제 실패한 뒤 원복됐고 독립 검수는 CLEAR다. 실제 SDK는 로컬 합성 자료와 Rules 인증 문맥을 사용했으며 실제 운영 로그인이나 운영 쓰기 시험이 아니다. 실제 커밋 뒤 응답 유실은 합성으로 재현했다.

총괄의 실제 컴포넌트 합성 화면에서 실패 입력 보존, 같은 등록 번호 재시도 성공, 다른 내용 보존과 명시적 기존 자료 열기, 기존 거래처 수정 재시도를 확인했다. 모바일 390px에서 문서 375/375px·대화창 349/349px로 가로 넘침이 없었다. 저장 중 입력·다른 거래처 열기·취소·중복 제출 차단도 확인했다. 운영 자료는 사용하지 않았다. 최종 빌드와 배포 결과는 후속 마감 기록으로 구분한다.

최종 앱 전체 타입과 양 앱 빌드는 종료 0이다. 관리자 22.50초·직원 15.53초, 양 PWA 생성·제품 9파일의 전후 SHA 일치·산출물 148개 manifest·FCM 원본 바이트 복원을 확인했다. 사전 생성과 check도 종료 0이며 독립 검수는 제품 9파일과 문서 3파일 모두 CLEAR다. 관련 고유 시험은 총 96개이며 전체 수천 개 시험을 반복하지 않았다.
