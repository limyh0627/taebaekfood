# 재고 추가·캔·박스 개봉의 최초 요청 보존

기준: 2026-10-12, 구현 전 기준 `e0c3395`. 아래 계약의 검증은 완료했고 배포·푸시 결과 확인 전이다.

## 문제와 변경 범위

품목 추가하기는 선택한 품목마다 재고를 따로 늘렸다. 앞 품목 저장 후 뒤 품목이 실패하면 전체 재시도에서 앞 품목이 다시 늘어날 수 있었다. 전체 선택과 결과 영수증을 한 Firestore 트랜잭션에서 저장한다. 기존 `anchorLotsByQty`, `canStockAfter`, `pruneDepletedLots`를 사용하며 수량·로트 계산을 새로 만들지 않는다.

캔과 박스 개봉은 UI에서 다시 실행할 때 새 작업번호를 만들었다. 성공 응답이 끊겨 재실행하면 같은 개봉을 다시 적용할 수 있었다. 회사·실제 로그인 UID·작업번호·시각·날짜·선택 및 환산 결과를 최초 요청에 보존한다. 캔은 기존 `UnpackPlan`, 박스는 대상 품목·낱개 수량·단위 kg를 고정한다. 현재 BOM이나 품목 정보로 보존된 요청을 다시 계산하지 않는다.

신규 박스 요청은 `boxItemName/unitItemName`도 최초 원문에 저장해 확인창과 재개 안내가 같은 품목명을 표시한다. 이름이 없는 이전 요청은 역할과 보존된 수량을 표시하며 문서 ID를 사용자 확인 문구에 노출하지 않는다. 이 표시 근거는 재고 단위나 환산 계산을 바꾸지 않는다.

## 저장과 재개

| 경로 | 원자 저장 | 결과 확인 근거 |
| --- | --- | --- |
| 여러 품목 재고 추가 | 모든 선택 품목의 재고·로트·조정 앵커 + 영수증 | `itemStockAddOperations`의 최초 요청과 결과 |
| 캔 개봉 | 캔·벌크 미러·원료 상태·원장 | 기존 `rawMaterialLedger`의 개봉 요청과 이동 결과 |
| 박스 개봉 | 박스·낱개 재고 및 로트·이동 기록 | 기존 `itemUnpackMovements`의 개봉 요청과 이동 결과 |

최초 원문은 로컬에 `prepared/submitted`로 보존하고 동일 원문인지 비교한 뒤 정리한다. 제출된 요청의 재개는 결과 조회만 수행한다. 영수증 부재를 미반영으로 확정하거나 새 입력으로 자동 재적용하지 않는다. 성공 영수증이 있으면 이후 품목 삭제·수동 조정 때문에 과거 작업을 다시 실행하지 않는다. 다른 회사·UID·입력을 같은 작업의 성공으로 인정하지 않는다.

동시 클릭은 첫 비동기 호출 전에 막는다. 확인창·인증 조회·저장 응답 이후에도 실제 회사·로그인과 화면 세대를 대조해 이전 결과가 새 모달이나 선택을 닫지 않게 한다. 로컬 저장 실패·손상 원문·결과 미확인은 기록을 지우지 않고 표시한다.

쓰기 큐와 커밋 시도 전에 자체 검사로 확실히 거절된 최초 실행은 응답 유실과 구분한다. 전체 품목 검사가 끝나기 전에 일부 품목을 저장하지 않는다. 확정 거절은 동일 원문 정리 후 입력을 고칠 수 있고, SDK·커밋·후행 로그인 변경 등 저장 결과가 불확실한 경우는 원문을 유지한다. 조회에서 영수증이 없다는 것만으로 확정 거절로 바꾸지 않는다.

## 권한과 제한

새 `itemStockAddOperations`는 기존 직원·회사별 Firestore 일반 규칙을 사용한다. 이번 변경은 Rules나 Functions를 변경하지 않는다. 클라이언트 영수증은 동일 요청의 결과 확인 근거이며 서버 서명이나 클라이언트 삭제를 막는 불변 감사가 아니다. 삭제된 영수증을 근거로 미반영 판정을 하지 않는다. 운영 DB 보정·이전 부분 저장 추정·과거 개봉 재생성은 수행하지 않는다.

`quantity_change`의 남은 요청 UI는 입고 예정 수량 변경을 설명하지만 현재 여는 경로가 없다. 관리자 두 소비자는 절대 재고와 증감 재고로 각각 처리한다. 과거 요청의 의미와 적용 여부가 불명확하므로 이번 변경에서 자동 변환하거나 새 계약으로 승격하지 않는다.

## 검증과 배포

최종 제품 freeze 후 집중 서비스·모델·회사 writer 감사 5파일 41 PASS, UI 관련 4파일 50 PASS, 실제 직원 Auth·Firestore SDK 3파일 11 PASS를 확인했다. SDK는 자기 합성 문서와 사용자만 정리하고 부재를 재조회했다. 초기 SDK 정리 guard가 해시 문서 ID에 원문 prefix가 없다는 이유로 실패한 세 경로는 정확 원문·UID 대조 후 별도 정리했고, 이후 최종 SDK도 정리까지 통과했다. 함수 결과만 성공인데 suite 정리가 실패한 초기 실행을 전체 성공으로 계산하지 않는다.
