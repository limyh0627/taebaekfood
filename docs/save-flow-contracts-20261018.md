# 주문·휴가 저장 계약

이 문서는 큰 화면 파일을 나누는 기준과 실제 저장 결과를 설명한다. 파일 수나 줄 수 감소를 전체 구조 개선의 완료 기준으로 삼지 않는다.

## 책임 경계

| 경계 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| 화면 | 입력·선택·렌더링, 현재 회사와 사용자 문맥 전달 | 업무 계산과 저장 성공 추정 |
| 제어 훅 | 저장 중 잠금, 초안, 요청 세대, 결과 안내, 확인·중단 동선 | 서버 요청 원문을 새로 조립하거나 계산 복제 |
| 업무 서비스 | 기존 공용 판정·계산의 조합, 저장 순서, 결과 해석 | React 상태 소유, 오류 코드를 근거로 미반영 단정 |
| 저장 경계 | 인증·회사 확인, 기존 원자 writer 또는 서버 명령 호출 | 다른 사용자로 후속 쓰기 계속 |
| 서버·규칙 | 권한과 자료 범위 강제, 원자 저장·영수증·중단 기록 | 화면의 관리자 표시나 로컬 사본을 권한 근거로 사용 |

## 공용 결과

`src/shared/saveOutcome.ts`는 결과 표현만 공유한다. 각 업무의 영속 요청이나 권한 프로토콜을 대체하지 않는다.

| 결과 | 의미 | 화면 동작 |
| --- | --- | --- |
| saved | 원 업무 ACK 확인 | 작성 완료 |
| rejected | 사전 검증 또는 정확한 명령의 확정 거절 | 원인·다음 행동 표시, 작성 내용 보존 |
| cancelled | 사용자 취소 또는 해당 요청의 서버 중단 확인 | 다른 요청의 취소·자료 삭제로 확대하지 않음 |
| unknown | 요청의 처리 결과를 확인하지 못함 | 원문 보존, 결과 확인·안전한 중단 제공 |
| partial | 원 업무 일부 또는 후속 처리의 결과만 확인 | 확인된 업무를 다시 보내지 않음 |

`partial`의 ID 목록은 원 업무만 나타낸다. 주문 저장 뒤 감사 응답이 끊겼다는 이유로 감사 기록이 없다고 단정하지 않는다. 원인과 사용자의 다음 행동을 함께 표시한다.

## 주문 편집

`orderEditService`가 기존 품목 변경 판정, 완료 주문의 추가 확인, 변경자 표시, 상태 계산, 단일 patch 저장, 후속 이력을 조합한다. 화면은 주문 문맥과 기존 writer를 연결한다.

- 날짜가 실제로 바뀌지 않으면 기존 출고 시각을 유지한다.
- 원 업무 ACK 전에는 수정창을 닫지 않는다.
- 원 업무가 저장되고 이력 결과만 미확정이면 완료 안내와 이력 확인 안내를 남긴다. 주문 전체를 재전송하지 않는다.
- 로그인·회사가 바뀐 뒤 이전 요청의 이력을 새 신원으로 쓰지 않는다.
- 통합 저장 콜백이 없으면 개별 날짜·품목·비고 저장으로 우회하지 않는다.

기존 주문 writer를 재사용한다. 이 분리가 주문 편집 전체에 새 CAS나 영구적인 중복 방지 프로토콜을 도입한 것은 아니다. 품목 전용 인라인 수정의 기존 0·음수·마지막 품목 삭제 정책도 이 구조 변경으로 재정의하지 않는다.

## 휴가 신규 저장

개인 신청과 관리자 단체 부여는 같은 `leaveRequestCommand` 계약을 사용한다. 화면의 일수 계산 정본은 유지하며 서버는 입력 형식·권한·대상과 원자성을 검사한다. 개인의 연차 발생·차감 정책을 새로 추정하지 않는다.

- 개인 신청은 한 건의 pending이며 직원은 본인만, 관리자는 같은 회사의 직원만 대상이 된다.
- 단체 부여는 관리자만 처리한다. 최대 400건·정규화 원문 256KiB를 전송 전에 검사하고 자동 분할하지 않는다.
- 모든 직원과 기존 휴가를 읽은 뒤 전체 생성과 영수증을 한 트랜잭션으로 저장한다. 대상 하나가 충돌하면 다른 대상도 생성하지 않는다.
- 같은 요청 ID와 원문은 영수증으로 재확인한다. 성공한 휴가를 나중에 삭제했더라도 늦은 재전송으로 되살리지 않는다.
- 조회 시 영수증 부재는 미확정이다. 명시적 중단은 영수증이 없어도 같은 요청에 중단 기록을 남겨 늦은 저장을 막는다.
- 저장과 중단이 경합하면 같은 영수증 문서가 직렬화 지점이 된다. 이미 저장된 휴가에 대한 중단은 그 휴가를 취소·삭제하지 않는다.
- 새 작성은 저장 결과 또는 서버 중단 결과를 확인한 뒤에만 허용한다. 로컬 원문을 지우는 것만으로 서버 요청을 취소했다고 보지 않는다.
- 관리자 알림은 신청 ACK 뒤의 후속 처리다. 현재 회사 관리자만 대상으로 하며, 대상이 없다고 전체 알림으로 바꾸지 않는다.

`leaveRequestOperations`는 클라이언트 직접 읽기·쓰기를 허용하지 않는다. 처리 결과는 인증된 명령의 조회로만 받는다. 기존 승인·변경·취소 처리 전체를 이 신규 생성 명령으로 전환한 것은 아니다.

## 검증 기준

구현 함수의 내부 순서를 복사해 시험하지 않는다. 실제 공용 업무 함수를 사용하고 다음 사용자 결과를 확인한다.

- 거절·확인 취소는 저장 0회, 저장 중 연타는 요청 1회.
- 업무 ACK 후 창 닫힘, 미확정·거절 시 초안 보존.
- 후속 기록 실패가 원 업무 재전송을 유도하지 않음.
- 새 로그인·새 초안에 옛 응답이 반영되지 않음.
- 같은 요청 재확인, 응답 유실 후 조회, 중단과 저장의 경합.
- 성공 뒤 자료 삭제 후 재시도로 재생성하지 않음.
- 같은 회사·역할의 UI 요청은 서버 계약과 일치하고, 금지된 직접 쓰기는 실제 Rules가 차단함.

실제 운영 자료로 시험하지 않는다. 로컬 SDK 검증, 합성 화면 검수, 운영 배포 확인은 별개 증거로 기록한다. 이번 범위를 다른 화면 전체의 저장 계약 통일 완료로 확대하지 않는다.

## 이번 검증과 남은 범위

- 확정 원문의 관련 시험 14파일 153건, 실제 로컬 서버 트랜잭션 8건과 Rules 2건을 통과했다. 시험이 잘못된 분류·경계 누락을 잡는지 의미변이로 확인하고 원문을 복원했다.
- 앱·서버 타입 검사와 관리자·직원 앱 빌드를 통과했다. 독립 검수에서 발견한 신규 알림의 부재 문서 조회 거절과 해시 불일치 원문의 중단 불가도 보완했다.
- 실제 화면에 합성 콜백을 연결해 PC·390픽셀에서 초안 보존, 중단 후 재작성, 응답 대기, 부분 완료 안내를 확인했다. 이 화면 검수는 실제 로그인·운영 서버 통신 시험을 대신하지 않는다. 실기기 검수는 사용자 지시로 제외했다.
- 1차에서 발견한 `HRManager.retirement.test.tsx`의 왼쪽 탭 정렬 기대는 이전 사용자의 오른쪽 탭 배치 지시와 맞지 않았다. 후속에서는 시험 fixture 전환과 함께 이 기대를 현재 양식에 맞게 바로잡았다. 제품의 탭 배치는 바꾸지 않았다.
- 1차 시점에는 기존 휴가 승인·변경이 직접 writer를 유지했다. 이때의 검증은 서버의 요청 영수증·동시 수정 보호 전환을 포함하지 않았다. 아래 후속 계약은 이 잔여 경로를 다룬다. 휴가 발생·차감 일수 정책은 재정의하지 않는다.
- 새 휴가 명령·Rules·클라이언트는 함께 배포해야 한다. 이번 개선본은 배포하지 않았으며 운영 자료도 변경하지 않았다.

## 승인·변경의 후속 계약

승인·반려·취소·변경은 신규 생성과 같은 명령·처리 영수증을 사용한다. 새 요청 형식만 구분하며 기존 생성 원문의 직렬화와 해시는 보존한다.

화면은 사용자가 본 휴가 행과 명시적 행동을 함께 넘긴다. 부모가 최신 목록에서 같은 ID를 다시 찾아 기대 원문을 바꾸지 않는다. 서버는 회사·신청자·기간·일수·상태·변경 요청·취소 자국의 값과 필드 존재 여부를 비교한 뒤 수정과 영수증을 한 트랜잭션으로 저장한다. 다른 사람이 먼저 처리했다면 충돌을 설명하고 현재 신청을 다시 확인하도록 안내한다.

- 개인은 승인된 본인 휴가의 변경·취소 신청을 보낸다. 관리자는 같은 회사에서 기존 결재와 즉시 취소를 처리한다.
- 일반 신청 승인·반려와 변경 신청 승인·반려를 구분한다. 변경 승인은 제안한 기간·사유·일수를 반영하며, 변경 반려는 기존 휴가를 유지한다.
- 이미 취소·반려된 휴가에 남은 변경 요청을 결재 대상으로 다시 노출하지 않는다.
- 취소 기록의 처리자는 인증된 직원 문서에서 가져온다. 화면이 보낸 처리자 이름으로 기록하지 않는다.
- 결과 미확정은 최초 행동과 기대 원문을 보존한다. 결과 확인과 명시적 요청 중단을 제공하며, 이미 적용된 행동을 중단한다고 기존 휴가를 되돌리지 않는다.
- 같은 원문 재확인은 기존 영수증을 반환한다. 대상 휴가가 이후 삭제돼도 재시도로 생성하지 않는다.

휴가 발생·차감 계산은 기존 공용 함수를 유지한다. 이 후속 계약은 2차 개선본에 구현했다. 배포 여부는 코드 검증과 별도로 구분한다.

## 2차 검증 결과

- 최종 동결 원문으로 관련 시험 18파일 166건, 실제 로컬 서버 트랜잭션 14건과 Rules 3건을 통과했다. 기존 생성 계약과 휴가 계산 회귀도 포함한다.
- CAS 제거, 직접 쓰기 허용, 잘못된 변경 승인, 미확정 창 닫기, 다른 대상 초안 닫기, 복구 참조 선택·저장 키 보호 등 의미변이 8건을 검출하고 원문을 복원했다.
- 앱·서버 타입 검사와 양앱 빌드를 통과했다. 빌드와 변이 시간이 겹친 첫 시도는 최종 증거에서 제외했으며, 마지막 수정 뒤에는 전후 원문 해시가 같은 동결본으로 빌드했다.
- 독립 검수와 실제 부품의 PC·390픽셀 합성 검수에서 원문 충돌 안내·초안 보존, 관리자 변경 승인 결과 확인, 다른 휴가의 결과 확인 뒤 현재 초안 보존, 미확정 변경의 중단 후 작성 재개를 확인했다.
- 합성 검수용 HR fixture의 옛 콜백 참조 오류는 fixture만 수정하고 화면을 다시 확인했다. 이를 제품 결함이나 서버 검증 결과로 세지 않는다.
- 운영 자료·실제 로그인·운영 RPC로 시험하지 않았다. 실기기 검수는 사용자 지시로 제외했고, 2차 개선본은 아직 배포하지 않았다.

## 3차 주문 편집 계약

앞의 주문 편집 절은 1차의 저장 경계다. 3차에서는 실제 수정 시작 시점의 주문 원문을 고정하고 서버에서 현재 주문과 비교한다. 부모가 최신 목록에서 주문을 다시 찾아 기대 원문을 바꾸지 않는다. 다른 사람이 품목·출고 상태 등을 먼저 수정했다면 초안을 남기고 현재 주문을 다시 확인하도록 안내한다.

- 주문 수정, 결정적인 ID의 수정 이력, 처리 영수증을 같은 트랜잭션으로 기록한다. 처리자 이름은 인증된 직원 자료를 사용한다.
- 응답을 확인하지 못하면 최초 요청을 보존한다. 같은 요청의 결과 확인과 명시적 중단을 제공하며, 로컬 사본 삭제만으로 서버 요청을 중단했다고 보지 않는다.
- 이미 처리된 요청은 영수증으로 확인한다. 주문이 이후 변경되거나 삭제돼도 늦은 요청으로 덮어쓰거나 되살리지 않는다.
- 수정창과 인라인 편집은 같은 저장 경계를 사용한다. 한 주문의 결과 확인이 다른 주문의 작성 중인 초안을 닫지 않도록 한다.
- 품목 변경 판정·변경자 표시·상태·수정 이력 계산은 기존 정본을 공유한다. 품목 전용 편집의 수량 정책과 날짜가 바뀌지 않았을 때의 기존 시각은 유지한다.
- 재고 처리 중인 구성·수량 변경과 재고에 영향 없는 표시·메모 변경을 구분한다. 기존 재고 writer와 catalog 참조 검증을 임의의 새 계산으로 대체하지 않는다.

결과 확인은 현재 수정창을 자동으로 닫지 않는다. 같은 주문을 다시 열어 작성한 새 초안이 이전 요청의 확인 때문에 사라지지 않도록 한다. 저장 완료 안내는 중립적인 결과 영역에 표시하고 오류로 표시하지 않는다.

실제 미확정 요청이 있을 때만 페이지 한 곳에 복구 영역을 표시한다. 행이 검색·페이지·보기에서 사라져도 정확한 대상과 요청 번호로 결과 확인·중단을 할 수 있다. 배송 화면이 내장 주문 목록을 사용할 때는 부모가 영역을 소유해 중복을 막는다.

기존 재고 경로의 직접 쓰기를 전면 차단하는 작업은 이 범위에 포함하지 않는다. 새 서버 명령·권한 규칙·앱은 함께 배포해야 하며 이번 개선본은 아직 배포하지 않았다.

## 3차 검증 범위

- 원문 충돌, 동시 편집, 늦은 재요청·명시 중단 경합, 감사·주문·영수증의 원자성, 재고 revision과 catalog 보호를 직접 시험했다. 실제 로컬 서버 SDK 10건과 새 권한 규칙 1건을 포함한다.
- 미확정과 확정 거절의 초안 보존, 같은 주문을 다시 연 초안 보호, 필터로 숨은 주문·없는 행의 복구, 실제 배송·택배 두 그룹에서 복구 영역 한 곳 유지를 회귀로 확인했다.
- 충돌 검사·감사 저장·감사 권한 보호·저장 키와 본문 결합·사용자 세대·초안·중복 표시 보호를 제거하는 의미 변이가 시험에서 검출되는지 확인하고 원문을 복원했다.
- 독립 검수에서 새 초안의 잘못된 닫힘과 배송 그룹의 중복 복구 영역을 발견해 수정했다. 해당 발견 전 빌드는 중단하고 최종 증거에서 제외했다.
- 운영 자료·운영 RPC·실제 로그인으로 시험하지 않았다. 합성 화면 검수와 로컬 SDK 검증을 구분하며 실기기 검수는 사용자 지시로 제외한다.
- 마지막 동결본에서 통합 시험 14파일 116건, 앱·서버 타입 검사와 양앱 빌드를 통과했다. 기존 계산·catalog·실행 호환성 관련 순수 시험 192건과 로컬 SDK·Rules 11건의 근거도 별도로 유지한다. 중복 실행을 신규 시험 수에 더하지 않는다.
- 최종 양앱 빌드는 입력 원문 전후 해시가 같았고 기존 FCM 파일을 복원했다. PC·390픽셀 합성 화면에서 저장 대기, 거절 뒤 초안 유지, 같은 주문을 다시 연 초안 보존, 중립 완료 안내, 목록 부재 요청의 중단 뒤 복구 영역 제거를 확인했다.
- 검수 자료에서 주문 거절을 휴가로 표기한 문구와 첫 로컬 서버 연결 실패는 합성 자료·검수 환경만 바로잡았다. 제품·운영 서버의 실패로 세지 않는다.

## 4차 품목 편집 계약

품목 정보가 저장된 뒤 구성품 저장이 실패해도 창이 닫히던 경로를 수정한다. 품목·박스 규격·BOM은 기존 재고 트랜잭션으로 함께 저장하며, 원가·배합·매입 연결은 실제 후속 응답을 구분한다. 기존 계산과 연결 정책을 새로 만들지 않는다.

- 기존 품목 수정은 update 의미를 유지해 삭제된 품목을 되살리지 않는다. 중복 문서 작업은 한 계획으로 합치고 쓰기 한도를 넘으면 나눠 보내지 않는다.
- 전체 작업 중 잠금을 유지하며 모든 단계의 성공을 확인한 현재 제출 세대만 창을 닫는다. 부분 완료와 미확정은 초안·단계 결과를 남긴다.
- 확인된 단계와 이미 업로드한 사진을 반복하지 않는다. 응답을 확인하지 못한 사진은 현재 품목이 아직 그 사진을 가리키지 않는다는 이유로 지우지 않는다.
- 회사·로그인·편집 세대가 바뀌면 이전 작업의 후속 쓰기와 다른 창 닫힘을 막는다.
- 원가와 배합 뒤 원가 계산은 같은 제출에서 저장한 품목·BOM을 반영한 입력을 사용한다. 저장 전 품목의 원가 방식으로 돌아가 새 수동 0원 등을 덮어쓰지 않는다. 계산 함수와 수율·반올림 기준은 기존 정본을 유지한다.

기존 품목 gateway에는 영속 처리 영수증과 취소 fence가 없다. 이 범위만으로 응답 유실을 완전히 종결할 수 있다고 보고하지 않는다. 현재 값의 일치·불일치를 특정 요청의 성공·미저장으로 추정하지 않으며, 안전한 최종 확인·취소까지의 후속 서버 계약은 별도로 확정한다.

## 4차 검증 결과와 후속 경계

- 동결본 관련 통합 시험 9파일 132건과 실제 로컬 SDK·Rules 시험 8건을 통과했다. Promise를 기다리지 않거나 원가에 옛 자료를 넣는 등의 의미 변이 8건을 검출·복원했다.
- 독립 검수에서 수동 0원 덮어쓰기의 primary·배합 두 경로를 발견해 같은 확정 snapshot으로 보완했다. 실제 원가 함수 회귀에서 수동 0원 보존과 자동 원가 150·상위 원가 300을 확인했다.
- 앱·서버 타입 검사와 양앱 빌드를 통과했다. 마지막 부모 타입 보완은 두 annotation을 제거한 소스 해시가 이전 동결본과 같아 런타임 변경이 없음을 독립 검수했다. 빌드 전후 원문 해시도 같았으며 기존 FCM 파일을 복원했다.
- PC·390픽셀 합성 화면에서 대기 중 잠금, 부분 완료의 단계 안내·초안 유지, 전송 전 거절의 입력 수정, 전체 완료 뒤 닫힘을 확인했다. 검수 도구가 순수 관계 함수를 원격 서비스로 오인한 오류만 수정했으며 운영 SDK·통신 차단은 유지했다.
- 운영 자료·실제 로그인·운영 RPC·실기기로 시험하지 않았다. 서버·권한 규칙·운영 배포도 변경하지 않았다.

다음 단계는 최초 원문·사진 경로를 영속 보관하고, 제한된 품목 편집 단계마다 실제 업무 쓰기와 서버 영수증을 같은 거래에 넣는 것이다. 완료된 단계는 유지하고 남은 단계만 중단하는 fence와 원문 CAS를 연결한다. 전체 원가 그래프를 요청에 넣어 정상 편집을 막지 않도록 필요한 projection의 순서 보존 digest와 서버가 검증한 작은 실행 계획을 사용한다. 후속 계약은 아직 구현·검증 완료로 세지 않는다.

## 5차 품목 편집 영속 복구 계약

4차의 현재 세션 단계 기록을 서버 영수증으로 확장한다. 새로고침 뒤에도 최초 제출 내용과 사진 경로를 복원하며, 현재 값이 같다는 이유만으로 해당 요청이 완료됐다고 판단하지 않는다.

- 제한된 품목 편집 명령만 받는다. 임의 컬렉션이나 필드 수정 요청을 실행하는 일반 명령으로 만들지 않는다.
- 최초 정규화 요청과 해시를 로컬에 기록하고 다시 읽어 확인한 뒤 전송한다. 회사·로그인·요청 번호·대상·단계가 맞는 서버 결과만 사용한다.
- 품목·규격·BOM, BOM 원가, 배합, 배합 뒤 원가, 매입 연결 순서로 처리한다. 각 단계의 실제 업무 쓰기와 처리 영수증을 같은 트랜잭션에 기록한다.
- 전 단계의 쓰기 수와 영수증 크기를 첫 업무 저장 전에 검사한다. 한도를 넘는 작업을 몰래 분할하지 않는다.
- 서버는 같은 회사의 실제 조회 결과와 원문을 대조한다. 새로 생긴 BOM·배합·연결도 충돌 검사에 포함하고, 이미 확인한 문서만 조회해 누락하지 않는다.
- 원가 계산은 4차에서 바로잡은 동일한 품목·BOM 확정 입력과 기존 계산 정본을 사용한다. 수동 0원, 단위·수율·반올림과 단가 0원·세금 삭제·포장 병합의 기존 의미를 보존한다.
- 응답을 잃으면 같은 요청의 결과를 확인한다. 완료 단계는 반복하지 않고, 완료 후 품목이 삭제돼도 늦은 재요청으로 되살리지 않는다.
- 명시적 중단은 이미 저장한 부분을 유지하고 남은 단계만 차단한다. 늦게 도착한 적용 요청과 같은 영수증 문서에서 직렬화해 중단 뒤 추가 저장을 막는다.
- 실제 미확정 요청이 있을 때만 복구 동선을 표시한다. 대상이 목록에서 사라져도 정확한 참조로 확인·중단할 수 있으며, 다른 품목의 새 초안을 닫지 않는다.
- 영수증이 없는 이전 방식의 미확정 요청을 새 방식의 안전한 요청으로 자동 승격하지 않는다.

이 절의 구현과 검증 결과는 아래에 기록한다. 운영 자료와 배포는 변경하지 않았다.

편집 시작 원문은 화면용 목록을 역으로 복원하지 않는다. 모달을 열 때 회사 조건을 붙인 서버 조회 네 건의 실제 문서 ID와 본문을 구분해 읽고, 전부 성공하기 전에는 저장하지 않는다. 조회 전후 계정·회사·작성창 세대가 바뀌면 결과를 버린다. 네 조회가 같은 순간의 스냅샷이라는 보장은 없으므로 첫 서버 트랜잭션에서 전체 근거를 다시 대조한다. 캐시 대체나 저장 클릭 때의 조용한 재조회로 최초 기대 원문을 바꾸지 않는다.

5차 구현에서는 편집창을 원문 조회 단계와 작성 단계로 나눴다. 실제 미확정 요청이 있을 때만 보이는 복구 목록은 대상이 삭제되거나 필터에서 빠져도 같은 참조로 상세·확인·이어하기·중단을 연다. 새로고침 복구는 보관한 사진 URL·경로를 사용하고 업로드 경로를 다시 타지 않는다. 서버에서 종결된 요청은 현재 자료를 다시 열어 새 요청을 작성한다.

서버 영수증에는 최초 요청과 검증한 단계 계획을 문자열 정본으로 저장한다. Firestore가 허용하지 않는 중첩 배열을 그대로 필드에 쓰지 않으며, 문자열 이스케이프까지 포함한 크기를 첫 업무 쓰기 전에 검사한다. 권한과 입력 형식을 통과한 요청의 확정 사전 거절은 원인과 처리 영수증을 남긴다. 통신 오류·손상된 영수증·신원 불일치를 확정 거절로 바꾸지 않는다.


## 5차 검증 결과와 남은 경계

- 기존 계산·gateway와 신규 서버 계약 129건, 화면 46건, 영속 요청 27건, 실제 로컬 SDK 10건과 Rules 1건을 통과했다. 고유 213건이며 마지막 통합 12파일 87건은 앞 시험의 재확인으로 중복 합산하지 않는다.
- 의미 변이 12건을 검출하고 원문을 복원했다. 완료 단계 재전송·원문/저장 키 결합·응답 정규화·수동 0원·낱개 안내·권한 우회·사전 거절 영수증·BOM 기본값·중단 뒤 버튼을 포함한다.
- 독립 검수와 SDK에서 중첩 배열 영수증 저장, 누락/null 수량 변환, 최초 확정 거절의 미확정 잔류, 중단 뒤 이어하기 표시를 발견해 보완했다. 최초 실패 결과와 보완 후 통과를 구분했다.
- 앱·서버 타입 검사와 양앱 빌드를 통과했다. 마지막 빌드 전후 입력 36개 파일의 해시가 같았다. 기존 FCM 파일을 원래 바이트로 복원했다.
- 실제 화면과 영속 요청 제어를 연결한 PC·390픽셀 합성 검수에서 최초 원인 안내, 새로고침 뒤 같은 요청 복원, 첫 완료 단계 재전송 없이 나머지 단계 복구, 완료·중단 뒤 버튼 정리를 확인했다. 전체 제출 완료만 작성창을 닫고, 결과 확인은 새 초안을 자동으로 닫지 않는다.
- 마지막 nullable guard 한 곳은 직전 소스와의 정확한 해시 역대조 및 독립 검수로 실행 동작이 같음을 확인했다. 앱 타입 검사와 해당 복구 시험도 다시 통과했다.
- 합성 응답 형식과 검수 도구의 정확한 문자열 선택 오류는 검수 자료에서 바로잡았다. 운영 오류로 세지 않는다. 검수 탭·로컬 서버·에뮬레이터와 자체 합성 자료를 정리했다.

새 서버 명령·Rules·앱은 함께 배포해야 한다. 이번에는 main 소스 반영까지이며 배포하지 않았다. 운영 자료·실제 로그인·운영 RPC로 시험하지 않았고, 실기기 검수는 사용자 지시로 제외했다. 다른 기능에서 쓰는 기존 직접 품목 writer를 전면 봉쇄한 것은 아니며, 이번 서버 명령은 품목 편집의 지정된 저장 경로에 적용한다.

## 6차 인사 저장 계약

직원 등록·수정은 완료 응답 전에 창을 닫지 않는다. 같은 작성 내용의 대상·요청 번호를 고정하고, 거절·응답 유실 시 초안과 원인을 남긴다. 회사·로그인·편집 대상이 바뀌면 이전 응답으로 새 창을 닫거나 후속 저장을 하지 않는다.

- 직원 생성·프로필·연차 조정은 제한된 명령으로 구분한다. 실제 직원 쓰기와 처리 영수증을 같은 거래에 넣고 원문 CAS, 같은 요청 조회, 명시적 중단과 늦은 저장 차단을 연결한다.
- 프로필이 소유한 입력과 연차 두 조정값만 받는다. 로그인·권한·FCM·급여 필드를 임의 수정하는 명령으로 만들지 않는다. 기존 회사 관리자·직원 권한 정책을 유지한다.
- 연차 보너스·이월은 입력마다 원격 저장하지 않는다. 직원별 두 값을 함께 편집한 뒤 명시적으로 저장하고, 구독 전 연속 수정으로 앞 값을 덮지 않는다. 다른 연차 필드와 기존 계산은 보존한다.
- 급여는 기존 원자 서버와 계산을 유지한다. 별도 초안 제어가 회사·UID·월·원본 revision·dirty를 소유하고, 다른 월이나 직원 목록 구독으로 미저장 내용을 초기화하지 않는다.
- 같은 월의 외부 변경은 충돌로 안내한다. 최신 자료를 명시적으로 불러오기 전에는 작성 시작 버전을 조용히 바꾸지 않는다. 저장 중 금액·지급일·지난달 복사를 잠근다.
- 급여 명령은 호출 시작 UID를 고정하고 모든 비동기 조회·권한 확인과 RPC 직전·응답 뒤에 같은 세대를 확인한다.

급여 초안 저장의 revision CAS와 급여 발행의 영속 영수증은 서로 다르다. 초안 응답 유실을 완전한 영수증 복구로 보고하거나 현재 값만으로 특정 요청의 ACK를 추정하지 않는다. 운영 자료와 배포는 변경하지 않았다.

## 7차 거래처 품목 조건 저장 계약

단가·과세·계정 한 건과 그 변경으로 새로 필요한 박스→낱개 연결 사슬을 한 원자 명령으로 저장한다. 안내는 쓰기 전에 끝내며 안내 중 원문이나 의존 연결이 바뀌면 업무 쓰기 없이 원인을 설명한다. 보드·목록·용역 화면은 같은 제어를 사용하고 완료 응답 전에는 작성값을 지우지 않는다.

- 단가 생략은 유지, 명시 0은 0원이다. 과세 null은 필드 제거이며 계정 생략과 포장 등 나머지 필드는 보존한다. 이미 있는 낱개 연결을 덮지 않는다.
- 좁은 관련 문서·조회 집합만 원문으로 고정하고 실제 서버 거래에서 다시 대조한다. 기존 BOM과 박스 환산 정본을 공유하며 새 계산을 만들지 않는다.
- 같은 요청의 결과 조회·명시적 중단·새로고침 복구를 제공한다. 늦은 저장을 봉쇄한 뒤 새로 작성하며, 현재 값만으로 특정 요청이 성공했다고 추정하지 않는다.
- 전표에서 여러 연결을 처리할 때는 각 단건의 완료를 구분한다. 앞서 완료한 연결을 다시 보내지 않으며 연결 저장과 전표 발행·원가 변경 전체를 한 원자 작업이라고 표시하지 않는다.

운영 자료와 배포는 변경하지 않았다.

앱·서버 타입 검사와 양앱 최종 빌드를 통과했다. 최종 빌드 전후 제품·시험 24개 파일의 해시가 같고 기존 FCM 파일을 원래 바이트로 복원했다. 첫 빌드 도중 시험 파일 끝 공백 한 곳을 정리한 일정 실수가 있어 첫 결과는 최종 동결 증거로 사용하지 않고, 공백만 달라졌음을 확인한 뒤 완전히 동결해 빌드를 다시 수행했다.

## 9차 기존 대상의 회사 권한 계약

직원 편집·거래처 품목 조건 저장·주문 수정 서버가 기존 대상의 회사 누락이나 null을 기본 회사로 허용하지 않도록 기존 직접 쓰기 Rules와 맞춘다. 실제 운영 자료에 이런 문서가 있다는 주장이나 운영 사고 확인은 아니다.

- 업무 대상은 명시적으로 현재 회사와 같아야 한다. 회사가 없거나 null·다른 회사면 업무 쓰기 없이 원인을 안내하고 유효한 요청의 거절 영수증으로 결과를 확인할 수 있게 한다.
- 같은 요청의 기존 완료 영수증은 대상 문서 검사보다 먼저 확인한다. 과거 완료 뒤 대상이 바뀌었다고 재처리하지 않는다.
- 신규 생성의 회사 주입, 인증 처리자의 기존 정책, 참조 자료 읽기의 기존 정책과 업무 계산은 이번 범위에서 바꾸지 않는다. 다른 모든 회사 fallback을 일괄 제거하지 않는다.

운영 자료 변경이나 배포는 하지 않았다.

## 9차 검증 결과와 남은 경계

- 회사 누락·null·타회사에서 업무 원문과 정밀 문서 버전이 그대로이고 거절 영수증만 남는지 확인했다. 주문은 재고나 카탈로그 검사를 거치지 않는 비고 수정도 포함한다. 거래조건은 준비 거절과 유효한 원문 apply의 거절을 나눠 검증했다.
- 정상 회사 저장·신규 회사 주입과 기존 처리자·참조 정책, 과거 완료 영수증의 우선 반환을 유지했다. 직원 SDK의 회사 누락 대상 수정을 정상으로 고정하던 옛 기대도 기존 Rules 계약에 맞게 바로잡았다.
- 보호 검사를 되돌리는 의미 변이 3건을 검출하고 원문을 복원했다. 직원은 실제 SDK가 잘못 적용된 결과를 잡았고, 거래조건은 실제 SDK의 잘못된 준비 허용을 잡았다. 주문은 실제 실행 함수의 비고 수정 오반영을 잡았다. 거래조건의 초기 mock 미구현 분기 오류는 별도 검출 성공으로 합산하지 않는다.

서버 전용 검사·안내 수정으로 UI 구조는 바꾸지 않았다. 실제 로그인·운영 자료·운영 RPC로 시험하지 않았고, 실기기 검수는 사용자 지시로 제외했다. 자체 SDK 자료만 정리하고 각 에뮬레이터를 종료했다. 앱의 모든 회사 누락 처리나 참조 정책을 일괄 바꾸지는 않았다. 이번에는 검증된 소스의 main 반영까지 진행한다.

최종 서버 세 경로의 독립 검수를 통과했고 소스·시험 9개 해시를 직접 대조했다. 앱·서버 타입 검사와 양앱 최종 빌드도 통과했다. 빌드 전후 9개 입력 해시가 같고 기존 FCM 파일을 원래 바이트로 복원했다.

## 10차 휴가 회사 권한 계약

기존 휴가 변경은 대상 휴가의 회사가 명시적으로 현재 회사와 같아야 한다. 관리자가 새 휴가를 등록할 때는 대상 직원의 회사도 명시적으로 같아야 한다. 단체 승인 부여뿐 아니라 관리자 본인·대리 pending 신청도 기존 Rules의 같은 관리자 분기를 따른다.

일반 직원 pending 신청과 변경 대상 직원 참조·취소 처리자의 기존 검사는 이번에 바꾸지 않는다. 처리 영수증 우선 조회, 원문 CAS, 단체 등록의 전부 성공 또는 전부 미등록, 중단 fence를 유지한다. 유효한 요청의 회사 불일치는 업무 쓰기 없이 원인과 복구 방법을 안내하고 거절 영수증으로 종결한다.

운영 자료 변경이나 배포는 하지 않았다.

## 10차 검증 결과와 남은 경계

- 실제 실행 함수의 순수 회귀 8건과 로컬 실제 SDK 19건을 통과했다. 고유 27건이며 반복 실행은 합산하지 않는다. SDK 기존 14건을 유지하고 신규 5건에서 일곱 변경 동작의 회사 누락·null·타회사, 관리자 단체 및 본인·대리 pending, 일반 직원의 기존 판독, 과거 완료 요청을 검증했다.
- 단체 대상 한 명의 회사 정보가 맞지 않아도 모든 휴가를 등록하지 않는다. 기존 휴가 거절 시 원문·정밀 문서 버전은 그대로이고 거절 영수증만 남는다. 완료 영수증이 있으면 대상 회사가 사라지거나 대상이 삭제돼도 새 업무를 하지 않는다.
- 두 보호 검사를 각각 되돌리는 의미 변이에서 실제 SDK가 잘못 적용된 결과를 잡았다. 두 실행을 분리해 각각 검출하고 원문을 복원했다. 시험 자료 생성 시 영수증 경로를 항상 자체 정리 목록에 등록하도록 시험의 누수도 보완했다.

서버 전용 검사와 원인 안내 수정이며 새 업무 규칙·RPC·DTO·Rules·UI·계산을 추가하지 않았다. 실제 로그인·운영 자료·운영 RPC로 시험하지 않았으며 실기기 검수는 사용자 지시로 제외했다. 자체 시험 자료만 정리하며 배포는 하지 않는다.

최종 3파일 독립 검수와 직접 해시 대조를 통과했다. 앱·서버 최종 타입 검사와 양앱 빌드를 통과했으며 빌드 전후 3개 입력 해시가 같다. 기존 FCM 파일을 원래 바이트로 복원했고 자체 에뮬레이터를 종료했다.

## 11차 견적 저장·삭제 수명 계약

견적 작성·수정·삭제의 실제 초안, 원본, 고정 번호와 요청, 대기·오류·복구 상태를 공통 제어 후크로 옮긴다. 저장 응답을 못 받아도 다른 ID로 새 문서를 만들지 않고, 같은 요청의 결과를 확인한다. 늦은 완료가 새 초안이나 다른 계정의 창을 닫지 않게 한다.

- 새 요청의 견적 snapshot을 전송 전에 고정·보관한다. 수정·삭제는 열 때 확인한 서버 원문의 정밀 버전을 비교하고, 신규는 대상 부재를 확인한다. 업무 쓰기와 처리 영수증은 같은 거래로 확정한다.
- 완료 영수증을 먼저 확인하므로 후속 수정이나 같은 ID 재생성 문서를 같은 요청이 다시 바꾸지 않는다. 미확정은 원문을 보존하고 결과 확인·명시적 중단을 제공한다.
- 기존 합계·세액·박스 단가·원가·날짜·견적번호 계산과 출력 미리보기는 같은 정본을 쓴다. 번호의 전역 유일 할당이나 새 업무값 제한을 추가하지 않는다.
- 수정은 UI 소유 필드와 사용자가 비운 선택 필드를 반영하고 나머지 상위 필드는 보존한다. 기존 줄에 포함된 미지 필드도 snapshot에서 보존한다.
- 새 처리 영수증만 서버 전용으로 보호한다. 구버전 앱의 기존 견적 직접 쓰기 권한은 유지한다. 새 요청의 CAS·영수증·중단 경계를 다른 직접 writer 전체의 봉쇄로 확대해서 설명하지 않는다.

운영 자료 변경이나 배포는 하지 않았다.

실제 저장 ACK 뒤 순서를 반영한다. 응답을 확인하지 못하면 자동 재송신하지 않고 최신 목록을 다시 조회한 뒤 사용자가 별도로 이동할 수 있게 한다. 이 조회는 최초 요청의 영수증 확인이나 늦은 쓰기를 막는 경계가 아니다. 다른 관리자의 동시 편집 CAS·영속 영수증·취소 fence와 초기 기본 분류 시드의 전체 원자 처리는 추가하지 않는다. 기존 분류 키·이름·숨김·사용 정책도 바꾸지 않는다. 운영 자료 변경이나 배포는 하지 않는다.

- 실제 부모 25건, 후크 8건, 순수 전송 계약 6건, 실제 로컬 SDK 5건, 회사 경계 정적 감사 2건, 고유 46건을 통과했다. 반복·중간 배치 구현 시험은 중복 합산하지 않는다. 최종 의미 변이 7건을 실제 assertion 실패로 검출하고 원문을 복원했다.
- root 검수에서 누락 타입에 매번 새 ID를 부여하면 응답 유실 뒤 중복 생성이 가능함을 확인해, 단일 배치 초안을 결정 ID와 단일 트랜잭션으로 정정했다. 기존 실 ID와 옛 타입 행은 보존하며 이관·삭제하지 않는다. 구버전 임의 ID writer 전체를 봉쇄한 것은 아니다.
- 실제 SDK에서 타회사인 둘째 대상이 거절되면 첫 대상도 바뀌지 않고, 정상 교환은 이름·숨김·미지 필드를 보존했다. 두 준비 요청의 누락 타입 ID 일치, 동시 트랜잭션의 타입 한 문서 생성과 기존 값 보존도 확인했다. 최종 TX를 문서별 TX로 나눈 변이에서 첫 문서만 반영되는 실제 부분 저장을 검출했다. 중간 배치 변이는 별도 이전 근거이며 최종 변이 수에 합산하지 않는다.
- 같은 UID의 회사 claim 변경은 callback 시작·쓰기 직전 재검사로 다음 쓰기를 막는다. 실제 서버 원문을 읽어 만든 ACK를 화면 확인 사본에 쓰며, 기본 plan의 이름으로 서버 이름을 덮지 않는다. 저장 중 모든 변경은 같은 잠금을 쓰고, 입력 중 draft는 닫기 확인 사본에 섞지 않는다. 최초 조회 대기·실패에는 확인 사본이 없으므로 optional onSaved를 호출하지 않는다. 현재 ItemManager는 이 callback을 사용하지 않아 이를 운영 목록 삭제 결함으로 과장하지 않는다.
- 정적 감사에서 기존 휴가 알림 TX의 검수 경로 등록 누락을 발견했다. 실제 UID·회사·알림 원문 및 수신자 Rules를 독립 읽기 검수한 뒤 해당 경로와 새 taxonomy 경로만 기존 transaction 검수 목록에 등록했다. 직접 addDoc·setDoc·writeBatch 금지는 유지하며 휴가 제품 코드는 바꾸지 않았다.
- 최종 타입 검사에서 발견한 회사 claim 전달의 weak type과 스냅샷 배열 타입을 명시했다. 세 변경을 역치환하면 이전 원문과 같고, 정본 함수가 읽는 companyId 값은 동일함을 독립 대조했다. 초기에 합성 UI mock export와 deferred 반환 자료가 맞지 않던 것은 시험 환경 문제로 구분하고 제품 결함 수에 합산하지 않는다.
- PC·390픽셀 실제 부모·후크·전송 경계에 합성 SDK만 연결해 ACK 전 순서 유지와 잠금, 오류 이유·진행 안내, 자동 재송신 없는 재조회, 새 명시 이동과 정상 ACK 뒤 순서 반영을 확인했다. 회사·UID 경합과 입력 blur는 실제 부모 회귀에서 검증했다. 실제 운영 로그인·DB·RPC를 사용하지 않았고 실기기는 사용자 지시로 제외했다.

다른 관리자의 동시 순서 수정 CAS·영속 영수증·취소 fence는 추가하지 않았다. 최신 조회는 최초 저장의 완료 증명이나 늦은 쓰기 봉쇄가 아니다. 기본 시드 전체와 기존 다른 generic writer의 응답 유실 프로토콜을 모두 원자 처리했다고 설명하지 않는다. 자체 에뮬레이터 자료만 정리하고 Java 및 8182 종료를 확인했다. 배포는 하지 않았다.

최종 앱·서버 타입 검사와 양앱 빌드를 통과했다. 빌드 전후 제품·시험 8개 해시가 같고 기존 FCM 원문을 복원했다. 최종 합성 UI 입력 3개도 동결 소스와 일치한다. 자체 검수 탭·로컬 서버를 종료했고 배포는 하지 않았다.

## 16차: 손익 계정 편집의 저장 응답과 명시 해제
- 계정 그룹·계정과목의 기존 편집 및 그룹 이동만 편집 후크가 소유한다. 실제 원본·초안·변경 항목·응답 미확정 항목·회사/로그인 UID·편집 수명을 함께 관리한다. 신규 등록·삭제 및 손익 계산 정책은 이번 범위 밖이다.
- 화면에서 수정한 표시 항목만 부분 저장한다. 손익 줄 미지정의 단순 표시는 변경이 아니며, 사용자가 기존 값을 해제한 경우에만 null을 전달한다. 저장 어댑터가 이를 Firestore deleteField로 바꾼다. 생략·undefined는 기존 값을 보존한다.
- 실제 부모 콜백이 저장 Promise를 반환한다. 지연 중 초안을 유지하고 중복 저장을 막는다. 거절·미확정은 이유와 다음 행동을 남긴다. 미확정 송신 항목을 원래 값으로 되돌린 경우에도 다음 명시 저장에 포함한다. 같은 회사·UID·편집의 확인된 ACK만 해당 편집을 끝낸다.
- 목록 갱신은 reload key 요청이며 조회 완료 응답이 아니다. 주업무 ACK 뒤 갱신 요청이 실패하면 저장 완료와 새로고침 필요를 구분해 안내하고 주업무를 다시 보내지 않는다. 명시 취소 후 늦은 결과는 다른 편집에 적용하지 않는다.
- 이는 기존 설정의 부분 쓰기다. 영속 처리 영수증·CAS·서버 늦은 쓰기 봉쇄를 추가하지 않았으며, 명시 재저장은 같은 필드의 동시 수정 값을 덮을 수 있다. 운영 자료로 시험하지 않는다. 실기기 검수는 사용자 지시에 따라 제외한다.
- 검증: 화면 10·후크 14·저장 어댑터 6·실제 부모 연결 9와 자체 demo 실제 SDK 3, 고유 42건을 구분해 검증했다. 의미 변이 9개에서 잘못된 동작의 회귀를 검출하고 원본을 복원했다. 그룹 이동의 불필요한 이름 검사 차이는 독립 검수에서 발견해 작업 의도를 구분하고 보완했다. 운영 자료가 아닌 실제 컴포넌트·후크·어댑터/차단 포트로 PC 및 390 너비를 확인했다. 실기기는 제외했다.
- 최종 앱·서버 타입과 관리자·직원 앱 빌드 통과. 전체 빌드 전후 소스·시험 9개 해시가 같고 기존 FCM 파일은 원본 바이트로 복원했다. 배포 및 운영 자료 변경은 하지 않았다.

## 17차: 계정 등록·삭제의 요청별 결과 확인과 복구
- 계정·그룹 등록 초안, 작성당 고정 targetId와 planId, 송신 원문, 삭제 대상·진행 상태는 lifecycle 후크가 소유한다. 등록·삭제도 실제 Promise와 공용 SaveOutcome을 반환한다. 기존 필수 입력·회계 필드·삭제 정책은 유지하며 편집·그룹 이동의 16차 저장 경로는 이 명령으로 바꾸지 않는다.
- 등록·삭제 전용 typed 서버 명령은 업무 문서와 처리 영수증을 같은 트랜잭션에 기록한다. 영수증 키와 검증은 회사·인증 UID·planId·reference 전체·원문 해시에 묶인다. 같은 요청을 다시 받으면 영수증을 먼저 읽으므로 이후 문서가 수정·삭제·재생성돼도 업무를 다시 적용하지 않는다. 삭제는 읽기 전용 open에서 선택 원문과 native 버전을 고정한 후 CAS로 확인한다.
- 응답을 놓치면 같은 요청 번호로 결과 확인한다. 영수증이 없다는 사실만으로 실패를 확정하지 않는다. 같은 원문으로 재시도하거나 명시 중단할 수 있다. 중단과 적용은 같은 영수증 키를 원자적으로 결정하므로 먼저 확정된 적용 완료 또는 적용 전 중단을 반환하며, 취소 뒤 같은 요청의 늦은 적용을 막는다.
- 클라이언트는 송신 전에 고정 요청을 영속 보관하고 다시 읽어 대조한다. 보관하지 못하면 송신하지 않는다. 재시도는 그 원문만 사용하며 현재 폼으로 재구성하지 않는다. 손상된 본문은 재시도하지 않고 유효한 reference로 결과 확인·중단만 한다. 로컬 부재도 서버 미처리의 근거가 아니다.
- 결과 확인과 중단은 reference로 서버 결과를 조회한다. 응답의 회사·UID·reference·상태·hash를 검증한 후 보관 원문과 별도로 대조한다. 같은 원문의 적용·거절·중단을 확인한 경우에만 해당 보관 원문을 정리한다. 다른 내용이 먼저 확정된 경우 이 기기 사본의 성공으로 오인하거나 자동 삭제하지 않고, 실제 서버 결과와 불일치 이유를 알린다. 정리 실패는 재조회 가능한 항목으로 남기고 업무 재실행을 유도하지 않는다. 복구 목록은 현재 회사·UID의 실제 영속 참조에서 구성하며, 이전 직접 쓰기의 세션 미확정 안내는 새 명령으로 승격하지 않는다.
- 이 기기 사본 정리는 별도 명시 행동이다. 서버의 확정 결과를 다시 확인하고 현재 기기 원문이 사용자가 관측한 원문과 같은 경우에만 로컬 사본을 삭제한다. 서버 결과가 아직 없으면 먼저 미처리 요청을 중단해야 하며, 그사이 사본이 바뀌면 삭제하지 않는다. 사본 정리를 업무 등록·삭제 성공이나 이미 적용된 업무 취소로 표현하지 않는다.
- 편집과 등록·삭제는 live busy 검사로 같은 tick의 교차 송신을 막는다. 같은 회사·UID·작성 수명의 ACK만 해당 초안을 정리하며 늦은 결과가 새 입력을 비우지 않는다. 업무 ACK 뒤 목록 갱신 시작 실패는 이미 완료된 등록·삭제와 구분해 안내한다.
- 이 영수증과 중단 fence는 해당 typed 요청의 보장이다. 기존 직접 쓰기 권한을 유지하므로 구버전의 별도 요청까지 취소했다고 주장하지 않는다. 운영 자료로 시험하지 않으며 실기기 검수는 사용자 지시에 따라 제외한다. 배포는 별도 상태로 기록한다.

### 17차 최종 검증
- 고유 132건(실제 부모 33·후크/어댑터 56·서버/Rules 16·관리자 연결 27)을 통과했다. 이 중 실제 로컬 SDK/Rules는 16건이며 운영 통신은 하지 않았다. 관련 최종 집중 7파일 116건과 중복 합산하지 않는다. 최종 계약의 의미 변이 15건을 검출하고 복원했다.
- 서버 결과 확인 뒤 같은 요청의 이전 잠긴 작성만 종료하는 실제 화면 결함을 보완했다. 다른 새 작성과 다른 회사·UID의 초안은 보존한다. 로컬 사본 정리는 업무 성공으로 처리하지 않는다.
- 잘못된 SDK 시험 import 경로의 옛 통과 로그는 근거에서 제외했다. 실제 서버 모듈로 해석되는 경로와 해시를 확인하고 최종 SDK 5건을 다시 통과했다. 시험 사례 삭제·skip으로 통과시키지 않았다.
- PC·390픽셀 합성 화면에서 응답 유실 뒤 실제 결과 확인, 서로 다른 사본의 서버 성공 설명, 명시 사본 정리 후 실제 계정 유지, 모달 내부 스크롤을 확인했다. 실제 부모·후크·전송 어댑터를 사용하고 외부 통신을 차단했다. 실기기는 사용자 지시로 제외했다.

최종 앱·서버 타입 검사 및 관리자·직원 앱 빌드를 통과했다. 빌드 전후 제품·시험 20개 해시가 같으며 기존 FCM 원문을 복원했다. 독립 검수는 최종 CSS 두 클래스까지 대조했다. 자체 UI 탭·서버를 종료했으며 이번 변경을 배포하거나 운영 자료를 수정하지 않았다.

## 18차: 전업무 복구 기준과 주문·품목의 다른 사본

전체 요구는 [업무별 실제 처리 상태 확인과 복구 종결](operation-recovery-coverage-20261019.md)에 별도로 추적한다. 계정 등록·삭제만의 개선은 전체 업무 완료가 아니다.

주문·품목 편집에서 서버에 A 원문이 확정된 뒤 같은 요청 번호에 유효한 B 사본이 남으면, 기기 hash를 서버 결과 조회의 필수 조건으로 보내 결과 확인과 중단이 반복 실패한다. 서버 요청 번호의 처리 상태 조회와 기기 사본의 일치 검사를 분리한다.

- 조회·중단은 요청 번호로 실제 서버 결과를 받은 뒤 회사·로그인 UID·대상·요청 번호와 응답 형식을 검증한다. 현재 기기 사본의 hash는 그다음 별도로 비교한다.
- 다른 원문의 성공을 현재 사본의 저장 성공으로 처리하거나 자동 삭제하지 않는다. 품목의 다른 원문에서 완료한 단계도 현재 초안 진행률에 합치지 않는다.
- 기기 사본 정리는 별도 명시 행동이다. 서버 종결 결과를 다시 확인한 후, 현재 기기 원문이 사용자가 관측한 원문과 같은 경우에만 정리한다. 서버 진행 중·미확정 또는 기기 사본 변경은 정리하지 않는다.
- 품목의 남은 단계 중단은 앞서 적용된 업무를 되돌리지 않는다. 사본 정리도 업무 완료 콜백·사진 삭제·새 초안 닫기를 실행하지 않는다.

서버·권한 규칙·운영 자료·배포를 변경하지 않는다. 독립 지불·문서함·OEM 근거 누락·재고 및 압착의 미처리 요청 종결은 별도 남은 범위로 유지한다.

18차 관련 고유 74건(주문 25·품목 전송 26·실제 UI/부모 배선 23)을 통과했고, 의미 변이 9건을 검출·복원했다. 최종 독립 검수에서 기기 사본 정리와 실제 업무 완료의 분리, 다른 원문의 진행률 승격 방지 및 관측 원문 비교를 확인했다. 타입 검사가 잡은 중복 조건은 앞선 unknown 조기 반환 뒤 항상 참인 조건만 제거했으며, 역치환 원문 일치로 실행 동치를 확인했다.

최종 앱·서버 타입 검사와 관리자·직원 앱 빌드를 통과했다. 빌드 전후 제품·시험 15개 해시가 같고 기존 FCM 원문을 복원했다. 자체 합성 검수 탭과 서버는 종료했다. 이번 변경은 미배포이며 운영 자료는 변경하지 않았다.

## 19차: 독립 수금·지불 결과 확인과 재열기 복구

최초 결제 원문을 현재 잔액·날짜로 재구성하지 않고, 모달을 다시 열어도 이전 요청의 실제 상태를 확인한다. 기존 전표 연결 수금의 검증을 공용으로 추출해 사용하며 금액·배분·전표번호·정산 계산은 바꾸지 않는다.

독립 조회와 미처리 중단은 기존 수금 요청 번호를 사용한다. 동일 번호의 중단과 적용은 원자적으로 경합하며, 이미 반영된 업무를 중단으로 취소하지 않는다. 서버 결과의 회사·UID·거래처·요청 번호를 검증한 뒤 기기 원문을 별도로 대조한다. 다른 원문 및 손상 사본은 자동 성공이나 자동 삭제로 처리하지 않는다.

새 요청은 본문과 별도의 참조 기록을 송신 전에 보관·확인한다. 과거 요청 번호까지 유실된 사본은 관련 처리 이력을 제한 조회하고 식별 한계를 설명한다. 이 기기 사본 정리와 실제 서버 요청 중단을 같은 결과로 표시하지 않는다.

서버 이력 조회는 현재 회사·인증 UID·선택 거래처의 단순 일치 조건과 문서 번호 순서로 20건씩 제한한다. 로컬 index 설정의 fieldOverrides는 비어 있고 [Firestore 공식 색인 문서](https://firebase.google.com/docs/firestore/query-data/index-overview)의 일치 조건 색인 병합 계약을 확인했다. 에뮬레이터 통과를 운영 색인 실행 검증으로 표현하지 않는다.

고유 239건은 화면·부모 44, 클라이언트 직접 59, 서버·공유 94, 기존 전표 복구 호환 42건이다. 서버·공유에는 실제 자체 SDK 71건이 포함된다. 최종 집중 10파일 168건은 이 합계와 중복 합산하지 않는다. 의미 변이 12개를 검출하고 원본을 복원했으며 최종 원문에 대한 독립 검수를 통과했다. 앱·서버 타입 검사를 통과했다.

실제 화면에서 응답 유실 뒤 원래 요청 재열기·조회·완료와 미처리 조회·중단·재작성 잠금 해제를 확인했다. 운영 통신이 차단된 합성 검수이며 실기기는 제외했다. 기기 정리가 실패하면 금융 완료와 남은 정리를 구분하고 창을 유지한다. 이미 중단·거절된 기록이라도 금융 변경 이력이 남으면 금융 미반영으로 단정하지 않는다.

최종 관리자·직원 앱 빌드를 통과했고 제품·시험 21개 해시가 빌드 전후 동일하다. 기존 FCM 파일을 원문으로 복원했다. 자체 화면 검수 탭·서버를 종료했다. 이번 변경은 미배포이며 운영 자료를 변경하지 않았다.
