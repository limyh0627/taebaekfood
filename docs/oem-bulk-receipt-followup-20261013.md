# OEM 벌크 입고의 원자 저장과 원가 연결

## 기존 문제

입고 모달은 벌크 kg 입력을 받지만 엔진과 서버는 모든 벌크 입고를 거절했다. 서버는 완제품이 없는 입고도 거절하여 벌크만 받은 배치를 완료할 수 없었다. 실패 요청은 최초 요청으로 보존되므로 다시 누르면 같은 미지원 입력이 재전송됐다.

옛 원료별 순차 저장을 다시 열면 완제품·원료·배치가 일부만 저장될 수 있다. 벌크 원료는 기존 원료 재고 코어의 입고 준비·원장·상태·미러 계산을 같은 OEM 입고 transaction 안에 연결한다.

## 저장 경계

새 앱은 실제 회사의 홀더 ID와 원kg를 보내고, 서버는 홀더·회사·재고 상태·기존 원장·OEM 발주·작업 영수증을 모두 먼저 읽는다. 명시 ID가 없는 옛 최초 요청도 같은 회사의 유일한 홀더가 확인될 때만 해석한다. 기존 완제품 전용 요청의 지문은 유지한다.

원료 입고의 고유 작업과 명령·원장 결과, 원입고 kg·실제 적용 kg·로트 ID를 OEM 영수증과 발주에 함께 남긴다. 원료 코어가 발급하는 로트 번호를 완제품 카운터 번호로 덮어쓰지 않는다. 기존 실사 소급 처리 의미를 유지하며 소급 입고를 현재 재고에 임의로 다시 더하지 않는다.

입고의 원가 근거가 없어도 기존 미확인 원가 정책으로 입고한다. 명시 근거가 있으면 제품 행과 벌크 행을 구분하여 같은 kg 배분 계산에 넘긴다. 가공비 후입력은 원입고 영수증·원로트 근거를 확인한 뒤, 품목과 원료 상태의 살아 있는 로트 원가 메타데이터를 같은 transaction에서 맞춘다. 원 수량·잔량·재고·원장 명령 해시는 변경하지 않고 이미 소진되거나 소급으로 만들어지지 않은 로트를 재생성하지 않는다.

## 범위와 잔여

벌크만 입고·완제품과 혼합 입고 및 같은 최초 요청 재전송을 지원하는 구현을 검증 중이다. 사용자 브라우저의 보존 원문을 자동 삭제하거나 새 수량으로 바꾸지 않는다. 입고 전 송출 취소의 기존 의미를 유지하며, 입고 완료 뒤 취소를 새로운 기능으로 구현한 것으로 표시하지 않는다.

운영 OEM 입고는 이 개발 검증에서 수행하지 않는다. 구현은 완료했고 통합 검수 중이며 아직 배포하지 않았다.

## 확인한 검증 결과

- 실제 로컬 Firestore transaction·입고 전 취소 경합을 포함한 서버 관련 4파일 33건 통과.
- 후가공비의 원입고 근거와 로트 원가 갱신 관련 3파일 51건 통과. 소비된 로트·소급 입고·수량 보존과 위조 근거 거절을 포함한다.
- 앱과 입고 엔진 관련 7파일 62건 통과. 전체 시험에서 발견한 옛 벌크 미지원 기대값 2건은 등록한 시험 파일에서 수정했으며 관련 2파일 18건이 통과했다.
- 전체 첫 실행은 535파일 중 534파일 통과, 4,907건 통과·2건 실패·7건 건너뜀이다. 실패 2건의 분리 재검증 통과를 전체 실행 성공으로 바꿔 표시하지 않는다.
- 앱·서버 타입 검사와 관리자·직원 앱의 실제 설정 파일을 사용한 빌드가 통과했다. 이후 추가된 매입 전표 UI 변경은 별도 검증 대상이다.

쓰기 제한과 원료·상품 중복 대상 보호, 원입고 근거 검사를 일부러 제거한 변이에서 시험 실패를 확인한 뒤 원복했다. 시험 자료는 에뮬레이터 합성 자료이며 운영 입고 자료 변경은 없다. 함수·Hosting 배포와 GitHub 반영은 별도 완료 기록이 필요하다.
