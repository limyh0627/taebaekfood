화면의 그룹·순서·묶음 초안, 원본, busy·검증·오류는 전용 후크와 application이 소유하고 부모는 포트를 연결하도록 옮겼다. 기존 같은 회사 직원 권한과 그룹·수량 정책은 유지한다. 초기화의 날짜 표기는 옛 무패딩 값과 같은 날짜로 비교한다. 권한 규칙에서 직접 쓰기를 닫는 범위는 해당 작업순서·그룹 설정·초기화 마커로 한정하고 다른 설정이나 메타 권한으로 확대하지 않는다. 관련 고유 154건(순수 서버 7·실제 Firestore SDK 15·권한 규칙 2·클라이언트 및 후크 61·화면 회귀 69)과 의미 변이 16개를 검증했다. root 집중 실행 137건은 이 수에 포함하며 중복 합산하지 않는다. 독립 교차 검수와 서버 타입·빌드, 양앱 빌드를 통과했다. 앱 타입도 최종 통과했으며 선언 보완 전후 실행 JS 동치를 독립 대조해 앞서 완료한 양앱 빌드 근거를 유지했다. 빌드 당시 입력 22개 해시와 기존 FCM 원문을 보존했다. 최초 타입 오류와 sandbox의 시험 준비 실패는 성공 근거에서 제외했다. PC 합성 화면에서 그룹 변경과 항목 저장의 응답 대기 중 창·초안 유지, 완료 후 연속 편집을 확인했다. 모바일 390픽셀 설정에서는 손상 사본과 결과 미확인 요청의 조회·중단·정리 후 실패 2건이 사라지고 새 편집이 가능한 것을 확인했다. 문서 영역 너비와 scrollWidth는 모두 375픽셀이었으며 가로 넘침은 없었다. 자체 서버·검수 탭·화면 크기 설정을 정리했고 운영 업무자료·실기기·배포는 변경하지 않았다. 원본 TODO 26완료·17잔여는 유지한다.

## 18차에서 연결한 범위

위 조사표의 주문 편집·품목/BOM 편집에서 다른 유효 사본 및 손상 사본 때문에 서버 결과를 조회하지 못하던 경로를 보완했다. 서버 요청 번호로 실제 결과를 확인한 뒤 기기 원문을 별도로 대조한다. 다른 사본의 완료를 현재 초안의 완료로 오인하거나 자동 삭제하지 않는다.

주문은 명시 사본 정리 후에도 정리 완료 안내를 남긴다. 품목은 다른 원문의 일부 완료 상태를 현재 진행률에 합치지 않고, 남은 단계 중단과 종결 확인 후 사본 정리로 이어진다. 사본 정리는 기존 업무·사진·새 초안에 영향을 주지 않는다. 실제 관리자 부모에서 주문 목록·배송 화면과 품목 복구 목록까지 새 포트를 전달한다.

관련 고유 74건과 의미 변이 9건을 검증했고 별도 담당의 독립 검수를 거쳤다. PC·390픽셀 합성 화면에서 실제 복구 UI·후크·저장 어댑터에 통신이 차단된 합성 서버를 연결해 결과 확인→중단→사본 정리를 확인했다. 운영 자료나 실기기로 시험한 것은 아니다. 이 결과는 독립 수금·지불·문서함·공지·나머지 저장의 공백을 해소했다는 뜻이 아니다.

## 19차에서 연결한 범위

독립 수금·지불의 재열기 복구를 연결했다. 기존 서버 영수증과 현금 최초 생성 이력의 검증을 공용으로 사용해 조회·미처리 중단을 처리한다. 모달은 현재 잔액이나 날짜로 이전 원문을 다시 만들지 않는다. 완료된 상계를 재실행하지 않는다. 조사표의 독립 수금·지불 행은 이 절과 긴급 22차의 현재 검증 범위를 반영했다.

## 20차에서 연결한 범위

## 21차 진행 범위

문서 파일 등록·삭제·메모 수정의 실제 결과와 남은 파일 정리를 연결했다. 업로드 전 예약과 고정 원문, 등록·삭제 영수증, 경로별 정리 예약, 서버 결과 확인과 새로고침 뒤 재개를 구현했다. File 자체는 저장하지 않으며 필요한 경우 같은 해시의 파일을 명시적으로 다시 선택한다. 본문 처리와 파일 정리를 분리하고, 다른 문서가 사용하는 파일이나 교체된 객체는 보존한다. 분류 CRUD·시드는 이번 완료 범위가 아니다.

검수 환경의 한계도 분리한다. Firebase Storage emulator 1.1.3은 실제 SDK의 세대 조건 삭제 요청을 무시해 이전 G1 조건으로 새 G2를 지우는 부정 시험이 실패했다. 이 결과를 통과로 바꾸지 않았다. Google 소유 [Storage Testbench](https://github.com/googleapis/storage-testbench) 0.45.0에서 실제 SDK의 이전 세대 조건 삭제가 HTTP 412로 거절되고 새 객체가 보존되는 것을 확인했다. 이 도구는 API 모델이며 실제 GCS·IAM 검증은 아니다. [Cloud Storage의 세대 조건 계약](https://docs.cloud.google.com/storage/docs/request-preconditions)과 로컬 모델 검증, Firebase 권한 규칙 검증을 각각 구분한다.

파일함 Storage 규칙의 Firestore 예약 조회는 배포 시 별도 서비스 에이전트 권한이 필요할 수 있다. 현재 운영 권한 보유 여부와 적용은 확인하지 않았다. 운영 권한이나 배포를 이번 구현·시험 승인으로 확대하지 않는다.

독립 검수에서 두 업로드가 같은 문서 번호로 등록될 때 나중 요청의 거절 뒤 파일 정리 경로가 사라지는 문제를 보완했다. 자기 예약을 닫고 본문 거절과 파일 정리 대기를 함께 기록한다. 다른 원문·계정의 예약은 닫지 않는다. 기기 사본이 교체되면 표시 이름과 정리 대상도 같은 관측으로 갱신하고 이전 File을 해제한다. 서버 미완료 목록은 기기 기록이 없어도 정확한 요청을 찾아 확인·중단·파일 정리를 이어가며, 빈 페이지의 다음 조회도 유지한다.

21차 고유 126건과 의미 변이 19개, 최종 독립 검수·타입·양앱 빌드와 실제 PC·390픽셀 합성 동선을 확인했다. 분류 관리 등 위 표의 나머지 미완료는 유지하며 이번 변경은 미배포다.

## 22차: 문서 분류의 결과 확인과 복구

분류 생성·삭제·기본 생성·경로 생성을 고정 요청과 서버 영수증의 같은 TX로 처리한다. 분류 삭제와 파일·중분류 생성은 같은 이름 범위의 fence를 사용하고, 파일 등록도 실제 분류 존재를 확인한다. 기본 분류는 회사 분류가 비었을 때 전체를 생성하고, 기존 중복 분류·이름·정렬을 임의 정리하지 않는다.

초기 진입은 로컬 원문을 읽고 해당 요청만 확인한다. 전체 서버 처리 이력은 사용자가 명시적으로 조회할 때 표시한다. 원문 손상·다른 사본·조회 실패·기기 정리는 업무 처리와 구분한다. 파일 복구와 분류 복구는 별도 후크가 맡으며 기존 파일 업무와 임베딩을 유지한다.
