# 전표 발행 거절과 재시도 잠금 복구

2026-10-13. 소스 수정·집중 검증 진행 중. 운영 gate 변경·커밋·배포는 하지 않았다.

최종 후속에서는 원 발행 감사에 `mutationRevision:0`이 추가된 표현 차이만 엄격한 해시 비교로 허용한다. 저장된 최초 요청 해시·회사·날짜·번호와 전체 감사 사슬은 계속 일치해야 하며 다른 필드나 0이 아닌 revision을 제외하지 않는다. 삭제는 거래처 후보 조회를 개별 전표·영수증 읽기 전에 수행하고, 외부 읽기 값은 순서 힌트로만 사용한다. 같은 transaction 안에서 회사·거래처를 다시 검증하며 힌트가 바뀌면 감사 쓰기 없이 `aborted`로 종료한다.

삭제 SDK 9개에서 동일 요청의 동시 삭제·정산·신규 선급 적용 경합과 고아 방지·현금 불변을 확인했다. 수동 정산의 연속 동시 경합과 CRUD 시험은 실측 약 9.854초로 기존 5초 제한을 초과했다. 설계 검토 후 해당 SDK 사례 하나만 30초 한도로 설정하고 동시 호출·모든 원문 및 updateTime 검증·정리를 유지했다. 마지막 실행은 4개 모두 통과했고 해당 사례는 실제 7.711초였다. 마지막 전체시험의 실패 5건은 직결 SDK 5파일의 최신 고유 64개 통과로 해소했으며, 재실행 결과를 중복 합산하지 않는다. 최종 후속 독립 검수도 신규 P1/P2가 없었다. 서버·양앱 빌드는 통과했으며 이후 서버 삭제 함수만 수정한 최종 Functions 빌드도 통과했다. 운영 적용은 화면 확인 이후다.

서버가 저장 전에 거절한 요청과 응답이 끊겨 결과를 모르는 요청을 구분한다. 최초 요청의 회사·사용자·작업 ID·원문·해시를 서버 영수증에 고정하고, 전표와 금전 자료를 저장하는 transaction에서 처리 완료를 함께 남긴다.

저장 전 거절을 확정할 때에는 해당 전표·금전 자료·변경 영수증·상계·주문·발주의 근거를 확인한다. 같은 ID를 사용할 수 있는 일반 전표·번호 전표·대출·수금/지불 서버도 같은 처리 영수증을 transaction에서 읽도록 연결한다. 다른 서버 발행 경로를 차단한다는 것은 **이미 고정된 동일 작업 ID의 뒤늦은 중복 저장을 차단**한다는 뜻이다. 정상적인 다른 ID의 발행과 정확한 기존 요청의 재조회는 보존한다.

무반영 확정은 일반 작성창의 `stmt-` ID에 한정한다. 별도 접두사를 사용하는 다른 업무에 근거 없이 확대하지 않는다. 서버 세대별 실제 배포·옛 세대 종료 근거가 없으면 조회 결과가 0이어도 무반영으로 확정하지 않는다. 이 준비 조건이 정상 신규 발행을 막는 조건이 되어서는 안 된다.

브라우저 잠금은 검증된 서버 거절 영수증과 로컬 최초 원문이 정확히 일치할 때에만 조건부로 해제한다. 다른 창에서 내용이 바뀌었거나 서버 결과가 미확정이면 최초 원문을 유지한다. 수량 0·비정상 숫자는 보내기 전에 막고, 안내와 재시도는 작성 창에서 볼 수 있도록 유지한다.

정상 날짜 변경·신규 발행·기존 수정·정확한 중복 요청·동시 발행과 거절 복구를 실제 SDK 9파일 214개 시험으로 검증했다. 에뮬레이터의 거래 잠금 시간 초과는 공통 배포 상태 → 카운터/전표 → 개별 요청 자료 순으로 조회를 통일하고 번호 초기화의 전체 조회를 개별 자료보다 앞에 놓아 해결했다. 기존 동시 실행을 유지했으며 동시 회귀 안의 요청 직렬화·임의 재시도를 추가하지 않았다. 보호 조건을 제거한 변이가 실패하는 것을 확인하고 원복했으며, 앱·서버 타입검사와 diff 검사가 통과했다.

이미 처리됐거나 삭제된 정확한 요청의 재조회는 이후 릴리즈 ID나 마감 날짜가 바뀌어도 확인할 수 있다. 새 저장에 필요한 배포 조건을 과거 처리 확인에 다시 요구하지 않는다. 독립 검수에서 이 범위의 신규 P1/P2는 없었다. 주문 요청 복구 경로와 최종 통합 검증·사용자 화면 확인을 마친 뒤 배포한다.
