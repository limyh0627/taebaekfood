# 전표 날짜 변경과 신규 번호 범위 검증

2026-10-13. 구현 검증 중이며 배포하지 않았다.

최종 후보에서는 새 날짜 카운터의 번호 근거를 전체 컬렉션 대신 해당 번호 접두 범위와 `tradeDate`·`date`가 해당 날짜인 문서의 합집합으로 조회한다. 두 원장의 각 세 단일 필드 query를 같은 transaction에서 실행하고 문서 ID로 중복을 제거한다. 회사 누락의 기존 태백 판정과 원래 번호 충돌 조건을 유지하며, 사전 조회는 회사·날짜·접두 범위가 일치할 때만 재사용한다. 범위 밖 전표의 수정 잠금과 불필요하게 교차하지 않도록 읽기 대상을 줄였다.

후속 순수 19개 및 범위·회사·사전 명세 보호를 제거한 변이 검증을 마쳤다. 원래 날짜 수정·신규 발행 `Promise.all`을 유지한 SDK 12개가 통과했다. 마지막 전체시험의 실패 다섯 건은 관련 SDK 다섯 파일의 최신 고유 64개 시험으로 모두 해소했으며 전체 6천 시험을 반복하지 않았다. 독립 검수에서 신규 P1/P2는 없었고 운영 배포는 아직 하지 않았다.

기존 검사는 신규 날짜의 번호 카운터가 없을 때 그 날짜에 연결된 전표를 모두 검사했다. 다른 날짜에 발행한 전표의 거래일을 옮기면 원래 발행 번호가 남아 있어도 신규 날짜의 발행을 막았다.

번호 사용 범위는 전표의 현재 거래일이 아니라 저장된 발행 번호의 접두사와 날짜로 판별한다. 정상 번호를 단 전표가 다른 거래일로 이동해도 그날의 신규 카운터 생성을 막지 않는다. 같은 번호 범위가 이미 사용됐는데 카운터만 없는 경우에는 임의로 0부터 재생성하지 않는다. 해석할 수 없는 번호나 실제 중복 가능성은 확인 대상으로 남긴다.

전표 날짜 수정은 기존 번호를 보존하는 수정 명령을 사용한다. 날짜 변경 자체가 신규 번호 발행이나 전표 처리 영수증의 초기화를 요구하지 않는다.

OEM에서도 번호 없는 실사 이월 로트는 번호 소비 근거가 아니다. 같은 날짜 번호를 가진 실제 로트의 물질이 불명확하거나 발주·처리 영수증에 번호 소비 근거가 있으면 중복 보호를 유지한다.

검증 대상은 날짜 이동 후 첫 발행, 기존 번호가 다른 날로 이동한 경우의 중복 방지, 회사·접두사 분리, 동시 최초 발행, 번호 없는 실사 로트와 실제 OEM 번호의 구분이다.

동시 처리 시험에서 거래 잠금 시간 초과가 재현됐다. 새 처리 영수증 검사를 제거한 비교 실행에서도 동일 오류가 발생했으므로 해당 검사만의 회귀는 아니었다. 공통 배포 상태 → 번호 카운터 또는 기존 전표 → 각 요청의 개별 자료 순으로 조회 순서를 맞추고 카운터 초기화의 전체 조회를 개별 자료보다 앞에 배치했다. 최종 금융 실제 SDK 9파일 214개가 통과했으며 기존 동시 실행을 유지했다. 동시 회귀 안의 요청을 직렬화하거나 임의 재시도를 추가하지 않았다. 보호 조건 제거 변이는 실패를 검출하고 원복했으며 타입검사·diff 검사와 독립 검수를 마쳤다. 최종 통합·배포는 아직 수행하지 않았다.
