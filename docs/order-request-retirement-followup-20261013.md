# 옛 최초 주문 요청의 보관과 정상 재개

2026-10-13. 구현·검증 진행 중이며 운영 승인정보 신규 적용·배포는 하지 않았다.

대상은 이전에 사용자가 수동 잠금 해제를 승인한 정확한 세 주문이다. 처리 결과가 미확정이므로 재고가 빠지지 않았다고 확정하지 않는다. 원래 잠금의 세대·회사·사용자·작업 ID·시작 시각·백업 근거가 맞는 승인정보가 있어야 한다.

운영 자료 읽기 전용 dry-run에서 세 주문 모두 잠금 해제 뒤 주문 본문이 바뀌고 후속 작업 기록이 생긴 것을 확인했다. 기존의 해제 직후 원문·버전이 그대로라는 계획은 적용하지 않는다. 현재 세 주문에는 `archive-only-current-evidence` 방식을 사용한다. 현재 주문과 작업 근거는 승인 당시 조회 기록으로 보존하되, 이후 메모·전표 연결·정상 작업이 바뀌었다는 이유로 옛 사본 보관을 다시 막지 않는다.

이 방식은 활성 승인 revision과 원래 세대·회사·사용자·백업, 현재 주문의 회사, 옛 세대가 현재 잠금으로 다시 활성화되지 않았는지를 확인한다. 해석할 수 없는 잠금은 추정하지 않고 보존한다. 최초 브라우저 원문을 terminal에 고정하고 다른 원문을 거절한다. terminal만 저장하며 현재 주문·재고·쓰기 버전·claim은 수정하지 않는다. 결과는 `unknown`, `archived-only`, `allowNewClaim:false`이며 같은 클릭에서 새 재고 작업으로 이어가지 않는다.

서버는 옛 브라우저 최초 요청 원문과 해시를 private terminal에 보존한다. 브라우저도 보관본을 저장하고 검증한 후 동일한 원문일 때만 활성 키를 조건부 해제한다. 원문이 다른 창에서 변경됐거나 승인 근거가 없으면 새 실패 잠금을 만들기 전에 멈춘다.

원료 작업 조회가 0이라는 사실만으로 자동 해제하지 않는다. 예전 앱이 요청을 늦게 다시 저장할 수 있으므로 실제 원료·품목·예약·완료 상태·job·원장 writer를 함께 차단하는 프로토콜이 필요하다. 현재 앱과 서버는 최초 조회의 쓰기 버전을 거래당 한 번 올리고, Rules는 옛 버전의 민감한 쓰기를 거절하도록 연결한다. 품목의 정상 삭제·재생성은 같은 transaction의 삭제 기록으로 연결한다.

잠금 해제 뒤 주문 원문·버전이 그대로인 별도 `unclaimed-after-unlock` 방식의 첫 claim은 단일 서버 명령으로 처리한다. 기존 `claim → reserve → 최초 raw 요청 저장 → effects` 순서를 유지하고 서버에 재고 계산식을 새로 만들지 않는다. 서버는 terminal·주문·실제 접촉 대상의 현재 상태를 같은 transaction에서 확인하고 claim 원문·소비 근거·주문 잠금을 함께 저장한다. 사이에 정상 입고·삭제·재생성이 있었다는 이유로 퇴역 당시 버전과 영원히 같을 것을 요구하지 않는다.

첫 claim 응답이 유실되면 보존한 정확 명세로 재개한다. 다른 명세는 같은 최초 요청으로 취급하지 않으며 이미 진행된 후속 세대에 옛 claim을 다시 설치하지 않는다. 이후 재고 효과는 기존 공용 예약·원자 명령이 최신 상태를 확인한다.

서버 퇴역 보관·클라이언트 CAS·첫 claim·완료 확인은 집중 6파일 133개 시험으로 검증했으며 실제 SDK 28개가 이 합계에 포함된다. marker·최초 원문·완료 후 재진입 보호를 제거한 변이는 각각 1·1·2개 실패를 검출하고 원본 bytes/SHA를 복원했다. 응답 유실 gateway는 별도 집중·SDK 39개가 통과하고 보호 조건 제거 변이 3종을 검출·복원했다. 앱·서버 타입검사와 diff 검사가 통과했다. SDK 통합의 callable 전송은 시험 adapter이며 실제 클라이언트 서비스와 서버 Admin transaction을 실행했다.

전체 늦은 writer는 앱·서버·Rules에 연결하고 정상 입고·실사·개봉·반품·삭제·재생성과 메타데이터 수정 보존을 검증했다. 동결본 독립 검수에서 신규 P1/P2는 없었다. 운영 읽기 전용 새 dry-run 종료0으로 정확한 세 건의 archive-only 백업 계획과 원승인 연결을 검증했다. 운영 적용 전 현재 자료 재조회·조건부 적용 및 되돌리기 검증을 수행해야 한다. 신규 승인정보 apply/undo·gate·배포·푸시는 실행하지 않았다.

전체시험에서 발견한 요청 사본 없는 일반 작업의 static Firebase 초기화는 실제 보관 사본 확인 뒤로 옮겨 해결했다. retirement 완료 가드는 실제 retirement 표시가 있는 반환에만 적용하며 정상 legacy 작업을 막지 않는다. 기존 시험 모형의 주문 조회·공용 회사 판정·AST 연결도 보완했다. 파일 간 공유 금융 fixture 충돌을 격리한 전체시험은 5,687개 통과·5개 실패·193개 건너뜀, unhandled 0이었다. 남은 5건은 직접 관련 SDK 5파일의 최신 고유 64개 통과로 해소했으며 전체를 반복하지 않았다. 이 합계의 퇴역 SDK는 28개다.

archive-only 승인정보 활성화도 현재 메모·연결·후속 작업의 원문/버전 변화만으로 막지 않는다. 승인 당시 snapshot은 이력으로 보존하고 원래 백업·세대·계정·회사·계획 해시 및 승인 CAS, 현재 주문 회사와 옛 세대 재활성 여부를 검증한다. 같은 순수 판독을 서버 보관과 승인 도구가 재사용한다. 해석할 수 없는 잠금은 거절하고 unclaimed 방식의 정확한 원문·버전·효과 검증은 유지한다. 최종 독립 검수에서 신규 P1/P2는 없었고 타입·서버 및 양쪽 앱 빌드는 통과했다. 신규 운영 승인정보·gate·커밋·배포·푸시는 아직 실행하지 않았다.
