# 작업완료 전 원료·부자재 부족 검사 · 2026-10-12

사용자는 부족한 상태에서 완료 처리를 시작하고 실패 잠금을 남기는 순서를 고치라고 요청했다. 현재 orderStockEngine의 status/line claim은 부자재 예약과 원료 소모 앞에 있고, 원료 job은 명령을 순차 저장하므로 뒤 원료의 부족을 앞 원료 저장 전에 전체 확인하지 않는다.

## 정확한 구현 범위

saved_raw_audit가 다음12파일을 맡는다: orderStockEngine.ts, orderRawInventory.ts/.test.ts, orderItemStock.ts/.test.ts, 신규 orderProductionPreflight.ts/.test.ts/.emulator.test.ts와 orderStockEngine.preflight.test.ts, 기존 changeOrderStatus.test.ts·boxStock.test.ts·produceIdempotent.test.ts의 이관된 원료 fixture 보완. 모두 src/features/admin 아래다. raw7의 사용자 복구 권한·Admin, purchase6의 주문/배송 카드와 겹치지 않는다. root는 이 문서와 UI 후속 문서·ERD·필드 사전5파일을 맡는다. 확대 노션 기록 최초 거절 뒤 사용자가 세 수정 전체 기록을 별도 승인했고 ORDER-UNLOCK 정확30 및 009·ERD 범위를 쓰고 재조회로 확인했다.

## 계약

생산 계획은 기존 planOrderProduction을 재사용한다. 예약 부족 계산을 orderItemStock에서 추출하여 실제 reserve와 읽기 전용 사전 검사에 함께 쓴다. 원료 명령도 orderRawInventory의 공용 builder를 실제 처리와 사전 검사에 공유한다. 원료 FIFO·혼합·앵커·원장 전용 명령은 prepareRawCommand의 기존 판정을 그대로 소비하며 별도 재고 계산을 만들지 않는다.

미완료 생산의 정방향 작업완료와 품목 체크는 claim 전에 최신 주문·대상품목·원료 문서를 읽고 전체 대상 줄의 누적 필요량을 검사한다. 다른 주문 예약, 기존 완제품으로 충당할 몫, 박스/낱개 입력과 부자재 BOM을 유지한다. OEM 원장 전용 원료 기록은 실물 원료 차감으로 오인하지 않는다. 부족이 있으면 전체 부족 목록을 안내하고 claim·예약·원료 job·생산기록 쓰기를 시작하지 않는다.

최종 독립 검수는 checked 전체이지만 producedAt이 없는 주문의 직접 출고완료·배송완료도 같은 생산 경로를 실행한다는 누락을 발견했다. 사전 검사를 DISPATCHED 한 상태에 제한하지 않고 STATUS_WANT_PRODUCED의 모든 신규 정방향 생산에 적용한다. 실제 두 직접 전환에서 부족 시 claim과 선행 쓰기0를 추가 확인한다. 기존 일반6523은 이 보완 전 중단하여 완료 증거가 아니며, 타입·양 빌드12619 종료0도 보완 전 결과로 구분한다. 최종 검사에서 미해결 P2를 그대로 배포하지 않는다.

검사 뒤 다른 주문과 경합할 수 있으므로 최종 저장 트랜잭션 검증은 유지한다. 이번 사전 검사는 여러 원료 저장의 완전 원자화나 모든 응답 유실 복구를 뜻하지 않는다. 역변경·이미 생산된 주문은 정방향 생산 부족 검사로 막지 않으며 저장된 복원 근거와 기존 복원 순서를 유지한다. 과거 일반 상태 실패의 불명확한 잠금을 임의 해제하지 않는다.

구현 회귀에서 같은 품목의 두 주문 줄이 앞선 줄의 생산 출력을 다시 기존 재고로 사용해 실제 원료 계획이 줄어드는 문제를 발견했다. 사전 검사만 더 큰 필요량으로 막아 두지 않고 공용 생산 계획의 작업별 배정 Map으로 실제 처리·예약 미리보기·사전 검사를 같은 계획으로 맞춘다. 이미 앞선 줄에 배정한 최종 출력은 후속 줄의 원품목·재귀 구성품 가용 재고에서 제외한다. 중간 계산은 최신 스냅샷에서 배정량을 뺀 뒤 생산 delta를 합하며, 먼저0으로 잘라 앞선 출력을 다시 쓸 수 있게 만들지 않는다. 원료 배합·BOM 비율·수량 단위는 바꾸지 않으며 과거 운영 기록을 다시 계산하지 않는다.

## 검증 계획

원료와 부자재 부족·여러 줄 합산 부족·다른 주문 예약·박스/낱개·혼합 로트·회사·실사 앵커 경계를 공용 계산으로 확인한다. 첫 원료가 충분하고 둘째가 부족할 때 claim 및 모든 선행 쓰기가0인지 실제 엔진 호출 순서로 시험한다. 정상 완료와 역변경 회귀, 보호 제거 변이, 실제 Auth·Firestore SDK 읽기와 쓰기0 및 합성 문서 정리, 독립 검토 후 전체 회귀·타입·양 앱 빌드를 확인한다. 아직 구현·검증 완료 기록이 아니다.

최종 관련9파일107시험·앱 타입·diff 검사가 통과했다. 실제 일반 직원(employeeId, isAdmin:false) Auth·Firestore SDK2시험에서 부족·정상·missing 검사의 원문 및 updateTime 불변과 쓰기0를 확인하고 합성 문서 및 사용자1개의 부재를 확인했다. 격리 Vite 변이의 사전 차단 제거3시험·배정 제거5시험·정방향 조건 제거3시험·역변경 보호 제거1시험 및 직접 상태 누락 재도입2시험 실패를 검출한 뒤 원본107시험을 재확인했다. 반복품목 stock0의1+1은 원료2·완제품2·로트2, stock1은 기존 충당1·원료1·추가 생산1을 실제 엔진 회귀로 확인했다. 재고 만들기·박스/BOM·OEM·완사입·역복원도 기존 공용 계약으로 검증했다. 최초 관련 fixture 부족 실패는 이관된 rawInventories 자료를 채워 시험했고 보호를 낮추거나 fake job일 때 우회하지 않았다.

독립 검수에서 직접 출고·배송완료 P2를 확인해 보완했으며 최종 저장본에서 해소와 추가 P1/P2 없음을 확인했다. 최종 전체81854는513파일4549시험 통과·7시험 skip, 종료0이며 앱/서버 타입 및 양 앱 빌드39174도 종료0이다. 사전75782 생성과 diff 검사를 통과했다. 사용자 승인에 따른 정확30파일 통합·서버/양 Hosting 배포를 진행하며, 실제 운영 배포와 GitHub 결과는 확인 뒤 별도로 기록한다.
