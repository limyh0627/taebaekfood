# 복식부기 전환 설계

> 작성: 2026-07-14 · 상태: **설계만, 미구현**
> 목적: 회계 코어를 복식부기로 바꿔 재무상태표·시산표를 뽑고, 지금의 추측 로직을 없앤다.
> **지금 당장 하지 말 것.** 7월 데이터가 이제 막 쌓이기 시작했고 신규 기능(자금원장·대체전표)이
> 실전 검증 전이다. 한두 달 안정화 후 착수.

---

## 1. 왜 하는가

### 1-1. 지금 겪는 문제는 전부 같은 병이다

현재 전표는 **반쪽 분개**다. `IssuedStatement.items[]`에 계정과목 하나 + 금액 하나뿐이고,
차변/대변이 없다. **상대 계정이 암묵적**이다(매입전표면 미지급금, 매출전표면 매출채권).

그래서 상대 계정을 알아야 하는 모든 계산이 추측이 된다:

| 지금 코드 | 하는 짓 | 위치 |
|---|---|---|
| `cfSectionOf` | 자산→투자, 부채→재무로 **추측**. 매입채무는 부채지만 영업이라 틀린다 | `financials.ts` |
| `apChg` | 매입채무를 `accrual − payIn`으로 **역산** | `financials.ts` |
| `isNoncashCode` | 감가상각을 **계정명 문자열**로 찾음 (`/감가상각|퇴직급여/`) | `financials.ts` |
| `cashDir` | 전표에 현금 방향을 따로 달아 부호 판정 | `types.ts` |
| `isOperating` | 자산만 달린 매입전표를 영업에서 빼는 특례 | `financials.ts` |
| `AccountGroup.cfSection` | 영업/투자/재무를 **사람이 태그** | `types.ts` |

복식부기면 **전부 자동으로 풀린다.** 상대 계정이 분개에 적혀 있으니까.

### 1-2. 못 하는 것

- **재무상태표를 못 뽑는다.** 자산·부채·자본 잔액을 집계할 방법이 없다.
- **시산표가 없다.** 차대 일치 검증 불가 → 회계 무결성을 보장 못 한다.
- **예수금·선급금·미수금을 못 쓴다.** 차변 1줄 : 대변 2줄을 표현할 수 없다.
  (예: 급여 300만 = 예수금 35만 + 실지급 265만)

ERP로 판매하려면 재무제표 3종과 시산표는 위생 요건이다. 경쟁 제품(더존·이카운트·뉴젠)은
전부 복식부기다.

## 2. 설계 원칙

### 사용자는 복식부기를 몰라도 된다

실제 ERP도 그렇다. 더존에서 매입매출전표를 끊으면 사용자는 거래처·품목·금액만 넣고,
뒤에서 분개가 자동 생성된다. 차변/대변은 안 본다.

```
[입력 레이어]   매출전표 · 매입전표 · 대체전표 · 자금원장     ← 지금 UI 그대로 유지
       ↓ 자동 분개 (auto-journalize)
[회계 코어]     journalEntries — 라인마다 (계정, 차변, 대변)
       ↓ 집계
[보고서]        시산표 · 손익계산서 · 재무상태표 · 현금흐름표
```

**지금 만든 UI는 하나도 안 버린다.** 전표를 끊으면 뒤에서 분개가 떨어지게만 하면 된다.

## 3. 데이터 모델

```ts
/** 분개 — 회계의 유일한 진실. 모든 보고서가 여기서 나온다. */
export interface JournalEntry {
  id: string;
  date: string;                 // 'YYYY-MM-DD' 회계 발생일
  lines: JournalLine[];         // 차변 합계 == 대변 합계 (불변식)
  memo?: string;

  // 이 분개를 만든 원본 문서 — 역추적·수정·삭제용
  sourceType: '매출' | '매입' | '대체' | '자금' | '수동';
  sourceId?: string;            // issuedStatements.id / cashEntries.id

  createdAt: string;
  createdBy?: string;
}

export interface JournalLine {
  accountCode: string;
  debit: number;                // 차변 (둘 중 하나만 > 0)
  credit: number;               // 대변
  partnerId?: string;           // 거래처별 채권·채무 원장용
  note?: string;
}
```

**불변식:** `sum(debit) === sum(credit)`. 저장 시 검증하고, 안 맞으면 거부한다.

### 계정과목에 필요한 것

지금 `AccountCode`에 `groupId`, `noncash`, (`AccountGroup.plLine`, `cfSection`)이 있는데,
복식부기로 가면 **`cfSection`과 `noncash`는 필요 없어진다** — 상대 계정으로 알 수 있으니까.

대신 필요한 것:
```ts
export interface AccountCode {
  code: string;
  name: string;
  type: '자산' | '부채' | '자본' | '수익' | '비용';   // 5분류 (그룹이 아니라 계정 자체에)
  normalBalance: 'debit' | 'credit';                // 증가가 차변이냐 대변이냐
  // 자산·비용 → debit / 부채·자본·수익 → credit
  isCash?: boolean;                                  // 현금성 계정 (현금흐름표 직접법용)
}
```

### 추가로 필요한 계정과목

지금 없어서 못 쓰는 것들:
- `254 예수금` — 원천세·4대보험 근로자부담분
- `295 퇴직급여충당부채` — 지금은 `535 퇴직급여충당금`을 비용으로만 쓰고 상대 부채가 없다
- `203 감가상각누계액` — 자산 차감 계정
- `108 외상매출금`, `251 외상매입금` — 지금은 전표에서 역산 중

## 4. 자동 분개 규칙

### 매출전표
```
(차) 외상매출금  1,100,000   [partnerId]
     (대) 제품매출              1,000,000
     (대) 부가세예수금            100,000
```

### 매입전표
```
(차) 원료매입      1,000,000
(차) 부가세대급금    100,000
     (대) 외상매입금             1,100,000   [partnerId]
```

### 대체전표 — 감가상각
```
(차) 감가상각비     833,000
     (대) 감가상각누계액           833,000
```

### 대체전표 — 급여 (예수금이 여기서 풀린다)
```
(차) 급여         3,000,000
     (대) 예수금                  350,000
     (대) 미지급급여             2,650,000
```

### 자금원장 — 지불 (매입전표 결제)
```
(차) 외상매입금   1,100,000   [partnerId]
     (대) 보통예금              1,100,000
```

### 자금원장 — 기계 구입
```
(차) 기계장치    50,000,000
     (대) 보통예금             50,000,000
```

### 자금원장 — 차입
```
(차) 보통예금    10,000,000
     (대) 단기차입금            10,000,000
```

## 5. 보고서가 어떻게 나오는가

전부 `journalEntries` 하나에서 나온다. 추측 없음.

### 시산표 (합계잔액시산표)
계정별 차변합·대변합·잔액. **차변 총계 == 대변 총계**면 무결성 OK.

### 손익계산서
수익·비용 계정만 집계. `type === '수익' | '비용'`.

### 재무상태표
자산·부채·자본 계정 잔액. **지금은 아예 못 뽑는 것.**

### 현금흐름표
`isCash` 계정(보통예금·현금·카드)이 움직인 분개를 뽑고, **상대 계정으로 영업/투자/재무를 가른다.**

```
현금 감소 + 상대가 기계장치(자산)   → 투자활동
현금 증가 + 상대가 단기차입금(부채) → 재무활동
현금 감소 + 상대가 외상매입금       → 영업활동
```

**`cfSection` 태그가 필요 없어진다.** 상대 계정이 답을 준다.
간접법도 순이익 + 비현금(감가상각누계액 상대 분개) 으로 자동 계산된다 —
`isNoncashCode` 문자열 매칭도 사라진다.

## 6. 이행 계획

### Phase 1 — 코어 신설 (기존 안 건드림)
1. `journalEntries` 컬렉션 + `JournalEntry` 타입
2. `journal.ts` 순수 모듈: 분개 검증(차대 일치), 시산표, 계정별 잔액
3. 계정과목에 `type`, `normalBalance`, `isCash` 추가 + 누락 계정 신설
4. 테스트

### Phase 2 — 자동 분개 (병행 운영)
5. 전표·자금 저장 시 분개를 **함께** 생성 (기존 로직은 그대로 둠)
6. 새 보고서(시산표·재무상태표)를 분개에서 뽑아 **기존 손익표와 대조**
   → 숫자가 맞으면 코어가 맞는 것

### Phase 3 — 전환
7. `computeMonthPL`, `computeCashFlowMonth`를 분개 기반으로 교체
8. 추측 로직 제거: `cfSectionOf`, `isNoncashCode`, `isOperating`, `apChg` 역산, `cashDir`
9. 기존 데이터 소급 분개 생성 (마이그레이션 스크립트)

### Phase 4 — 정리
10. `AccountGroup.cfSection`, `AccountCode.noncash` 제거
11. 거래처원장을 분개 기반으로 (지금은 전표+결제 역산)

**Phase 1·2는 기존 기능을 전혀 안 건드린다.** 병행 운영하며 숫자를 대조할 수 있어서 안전하다.

## 7. 주의할 것

- **부가세.** 지금 전표에 `supply`/`tax`가 있는데 분개로는 `부가세대급금`/`부가세예수금`
  계정이 필요하다. 부가세 신고서까지 뽑으려면 세금계산서 발행분/수취분 구분도 있어야 한다.
- **기존 데이터 소급.** 132건 전표 + 자금 기록을 분개로 변환해야 과거 재무상태표가 나온다.
  안 하면 시작 시점의 기초잔액만 수동 입력하고 그 이후부터 쌓는다(더 현실적).
- **원가.** 재고자산(원료·재공품·제품)의 원가 흐름은 별개 문제다. 지금 `inventorySnapshots`로
  월말 재고액을 직접 입력해 우회 중. 복식부기와 별개로 나중에 손봐야 한다.
