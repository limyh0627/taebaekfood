# 상환 계좌 미지정: 장부 귀속 대조와 정정 흐름

확인일: 2026-10-07. 원본: [TODO-LOAN-REPAYMENT-ACCOUNT-LEDGER-20261002](https://app.notion.com/3ed2cda7782b8189b5d8e9eb44be0d78).

이 문서는 기존 계산 대조와 표시·정정 흐름 설계 및 같은 날 추가된 사용자 기본계좌 결정을 기록한다. 미지정 상태를 별도로 관리하는 새 UI나 운영 정정 버튼은 구현하지 않았다. 일반 분개·계좌별 잔액·대출 원금 계산식은 유지한다. 아래 추가 승인 범위의 기존 계좌 귀속 정정만 실행했다.

## 확인한 현행 동작

`src/shared/autoJournal.ts`의 `journalizeCashEntry`는 현금 계좌 ID가 계정 매핑에 없으면 103으로 분개한다. 공란뿐 아니라 삭제된 계좌 ID나 누락된 매핑도 해당한다. `src/features/admin/cashLedger.ts`의 `buildAccountLedger`와 `totalCashOnHand`는 계좌 ID가 일치한 거래만 포함한다. 일반 분개에 103이 있다는 사실로 특정 통장을 추정하면 안 된다.

`src/shared/loanLedger.ts`는 같은 회사·같은 loanId·기초일 이후 거래의 대출 계정 줄을 읽어 원금을 계산한다. 따라서 은행 귀속을 몰라도 원금 감소는 계산될 수 있다. LoanManager의 신규 차입·상환은 계좌 선택을 이미 필수로 요구한다. 이 보호가 과거 공란 자료를 소급해서 고치지는 않는다.

## 실제 함수로 대조한 가상 사례

기초 통장 1,000원, 기초 대출 500원에서 원금 100원과 이자 10원을 상환한 단일 사례를 현행 순수 함수로 실행했다. 운영 데이터베이스 접근은 없다.

| 현금 계좌 ID | 일반 분개의 출금 계정/금액 | 등록 통장 잔액 합계 | 대출 원금 잔액 |
| --- | --- | --- | --- |
| 공란 | 103 / 110원 | 1,000원 | 400원 |
| 확인된 bank-a, 매핑 10301 | 10301 / 110원 | 890원 | 400원 |
| 등록되지 않은 deleted-bank | 103 / 110원 | 1,000원 | 400원 |

재현 파일: `work/loan-account-attribution-probe-20261007.mts`. 결과: `work/loan-account-attribution-probe-20261007.json`. 실행 exit 0. 이는 현행 함수의 귀속 차이를 확인한 자료이며 운영 자료의 미지정 건수나 금액을 확인한 결과는 아니다.

## 표시 계약 제안

회사와 조회 기간을 먼저 제한한 자금 거래에 대해 다음 상태를 구분한다. 대체전표는 실제 입출금이 아니므로 공란 계좌 대상에서 제외한다.

- 계좌 ID 공란: `출금 계좌 미지정` 또는 `입금 계좌 미지정`.
- ID는 있으나 같은 회사의 등록 계좌를 찾지 못함: `계좌 확인 필요`. 삭제된 계좌와 타사 계좌를 임의로 동일시하거나 이름을 노출하지 않는다.
- 계좌는 확인됐으나 회계 계정 매핑 없음: `계좌 계정 연결 필요`. 계좌별 잔액 귀속은 알 수 있지만 일반 분개의 계정 귀속은 별도 확인해야 한다.
- 비활성 계좌라도 같은 회사에 실제로 등록된 과거 계좌라면 역사적 거래의 귀속은 유지한다. 신규 선택 가능 여부와 분리한다.

미지정 금액은 개별 통장 잔액과 구분해 건수·입금·출금 합계로 표시한다. 103 합계와 모든 통장 잔액 합계를 자동 일치시키거나 특정 통장에 나눠 넣지 않는다. 대출 원금 계산은 기존 분개 기준을 유지한다.

## 정정 흐름 제안과 구현 경계

관리자가 회사·문서 ID·거래일·원금·이자·현재 계좌 상태를 확인하고, 은행 거래 근거로 실제 계좌를 선택한다. 제출 전에 일반 분개와 선택 통장 잔액의 변경 전후를 보여준다. 원금·이자·금액·거래일·loanId는 계좌 정정에서 바꾸지 않는다.

운영 정정은 기존 승인된 금융 명령 경로의 사용 가능 여부를 먼저 확인해야 한다. 문서 버전과 이전 cashAccountId를 재확인하고, 같은 요청의 중복 처리를 막으며, 회사 경계를 서버에서 확인해야 한다. 발행 전표의 계좌를 클라이언트 직접 수정하거나 차액을 새 자금전표로 만들어 보정하지 않는다. 이 저장 계약과 정정 이력/취소 계약을 검증하기 전에는 정정 버튼을 구현하지 않는다.

현재 loanMovementCutover는 두 회사 모두 활성 근거가 없으며 이를 켜지 않았다. 기존 022 금융 후보와 이 설계는 금융 운영 전환 승인으로 확대하지 않는다. 아래의 사용자 명시 계좌 정정은 이 컷오버 활성화와 별개다.

실제 회사별 미지정 자료를 읽기 점검하고 출금 근거를 확인한 뒤 표시 UI 범위를 확정한다. 저장 기능은 서버 명령·컷오버·정정 이력 계약을 검증한 후 별도 범위로 진행한다. 원본 TODO 전체 완료가 아니다.

## 추가 사용자 결정과 적용 결과

사용자는 2026-10-07 신규 전표의 기본 계좌를 메인으로 지정하고, 태백의 계좌 미지정 기존 전표도 모두 연결하라고 명시했다. 메인통장은 농협은행 351-0526-3164-13이다. 기존 `cashacct-temp-main` ID를 유지하고 계좌 이름을 `농협은행 351-0526-3164-13 (메인통장)`으로 변경했다. 이름을 바꿔도 ID를 참조하는 전표 연결은 유지되며 삭제 후 재생성으로 ID를 바꾸면 자동 이전되지 않는다.

운영 정정은 태백(회사 필드 없는 옛 태백 포함)의 미지정 입금 153건·출금 88건, 합계 241건에 cashAccountId만 연결했다. 계좌 이름 1건과 함께 전체 242건을 단일 트랜잭션으로 변경했다. 대체전표의 빈 계좌와 기존 지정 계좌·금액·일자·전표번호는 유지했다. 계좌 연결 후 통장 원장 귀속은 변경되지만 대출 원금 계산과 일반 103 분개 계산식은 변경하지 않는다.

변경 전 각 필드 존재 여부/값과 전체 Firestore Timestamp(seconds/nanoseconds)를 백업하고, 원문 버전·회사·금액·일자·방향을 확인한 뒤 적용했다. 독립 검수 후 적용 exit 0, 전 대상 재조회 verified true이며 별도 읽기 확인에서도 태백 미지정 입출금은 0건이었다. `work/set-taebaek-main-account-20261007.mts`는 dry가 기본이고 같은 백업에 대한 `--undo`가 있다. 백업 `work/taebaek-main-account-backup-v2-20261007.json`, 결과 `work/taebaek-main-account-apply-20261007.json`, 별도 확인 `work/taebaek-main-account-verification-20261007.json`을 남겼다. v1 미리보기 백업도 보존했다.

신규 입력 기본값은 표시 이름 대신 같은 회사 활성 계좌의 고정 ID를 우선한다. 직접 선택한 계좌는 유지하고, 다른 회사 메인 계좌를 대신 쓰지 않는다. 관련 입력 화면과 빈 입출금 저장·수동 정기발행에 적용한다. 이 변경은 서버 금융 명령/월 자동 발행 Functions의 재배포나 상환 컷오버 활성화를 포함하지 않는다. 새로운 미지정 상태 관리 UI와 일반 정정 버튼 구현까지 전체 TODO 완료로 주장하지 않는다.
