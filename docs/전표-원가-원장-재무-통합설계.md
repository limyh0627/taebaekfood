# 전표·세금계산서·원가·원장·재무 통합 설계

- FigJam: [태백푸드 회계·전표 상세 설계](https://www.figma.com/board/SnQRYswn0dSftdBjyiukKD)
- 작성일: 2026-09-10
- 범위: 전표, 세금계산서·계산서, 거래처별 단가·과세, 품목 원가, 거래처 원장·통계, 재무제표

FigJam은 설명용이다. 구현할 때의 기준은 이 문서와 공용 함수의 시험이다.

## 1. 최종 구조

회계 기록은 쓰기와 읽기를 가른다.

```text
화면
  → 전표 명령(발행·수정·취소)
    → issuedStatements / cashEntries / settlements
      → Voucher 통합 읽기
        → JournalEntry 분개
          → 거래처 원장·통계 / 손익·재무상태·현금흐름
```

`issuedStatements`는 거래가 발생한 근거, `cashEntries`는 실제 돈이 움직인 근거다. 저장 컬렉션은
둘이어도 읽을 때는 [vouchers.ts](../src/shared/vouchers.ts)와
[buildJournals.ts](../src/shared/buildJournals.ts)를 반드시 거친다. 거래처 원장과 통계, 재무제표가
각자 전표를 다시 세면 같은 거래가 화면마다 다른 숫자로 나온다.

## 2. 전표 쓰기

현재 [TradeStatement.tsx](../components/TradeStatement.tsx)가 전표 저장, 주문 연결, 거래처 단가,
품목 원가, 매입 입고카드를 차례로 갱신한다. 앞 저장이 성공하고 뒤 작업이 실패하면 재시도 때
중복되거나 일부만 반영될 수 있다. 최종 구조에는 `statementCommand.ts`를 만들고 발행·수정·취소의
단일 진입점으로 쓴다.

### StatementCommand

| 필드 | 역할 |
|---|---|
| `operationId` | 같은 클릭을 재시도해도 한 번만 반영되게 하는 작업 ID |
| `kind` | `ISSUE`, `EDIT`, `REVERSE` 중 수행할 일 |
| `statementId` | 전표의 영구 ID. 수정해도 바꾸지 않는다 |
| `expectedVersion` | 읽은 뒤 다른 사람이 먼저 고쳤는지 확인하는 버전 |
| `companyId` | 어느 회사 장부인지 정하는 키 |
| `partnerId` | 거래처 이름 대신 쓰는 연결 키 |
| `tradeDate` | 손익·원장에 반영되는 회계 발생일 |
| `orderIds` | 전표에 묶인 주문 ID 목록 |
| `lines` | `itemId`, 수량, 세금 포함 단가, 과세 구분, 계정과목 |

### 저장 규칙

1. `statementLines`로 주문·수기 입력을 같은 줄 모양으로 만든다.
2. `lineAmount`로 줄별 공급가액·세액·합계를 확정한다.
3. `itemId`, `partnerId`, 계정과목, 수량, 단가와 합계를 검증한다.
4. `operationId` 중복과 `expectedVersion` 충돌을 확인한다.
5. 전표 본문, 주문 연결, 거래처 현재 단가, 품목 현재 원가와 원가 이력은 Firestore transaction으로
   함께 저장한다. 이 가운데 하나라도 실패하면 전부 반영하지 않는다.
6. 매입 입고카드도 전표 발행의 필수 결과라면 같은 transaction에 넣는다. 알림·외부 전송처럼
   원본 장부가 아닌 작업만 `AfterCommitJob`에 남겨 재시도한다.
7. 취소는 기존 전표를 삭제하거나 과거 값을 덮지 않고 `REVERSE` 기록을 뒤에 쌓는다.

반환값은 `applied`, `duplicate`, `rejected`를 가른다. `rejected`에는 명령 원문을 실행값으로 쓰는
것이 아니라, 어떤 입력이 왜 거절됐는지 다시 보여 주고 안전하게 재시도하기 위한 문맥으로만 담는다.

## 3. 전표 줄과 금액 스냅샷

전표 줄은 `lineKind`로 품목 줄과 계정 줄을 가른다. 품목 줄은 `itemId`가 필수이고, 임대료·급여처럼
실물 품목이 아닌 계정 줄은 `itemId` 없이 `accountCode`가 필수다. 지금처럼 `itemId?: string` 하나로
두 뜻을 표현하면 누락된 품목 줄과 정상적인 비용 줄을 구별할 수 없다.

`IssuedStatementItem`은 현재 마스터를 가리키는 ID와 발행 당시 표시값을 같이 가진다.

| 필드 | 기준 |
|---|---|
| `lineKind` | `item` 또는 `account`. `itemId`가 없는 이유를 명확히 한다 |
| `itemId` | `item` 줄의 필수 품목 연결 키. 이름으로 다시 찾지 않는다 |
| `name`, `spec` | 발행 당시 인쇄용 스냅샷 |
| `qty` | 발행 당시 수량 |
| `price` | 사람이 확정한 세금 포함 단가 |
| `isTaxExempt` | 이 거래처·이 품목의 발행 당시 과세 판단 |
| `supply`, `tax`, `total` | 발행 시점에 확정한 금액 |
| `accountCode` | 발행 당시 분개 계정 |

과거 전표는 현재 품목명, 단가, 원가, 과세 설정이 바뀌어도 다시 계산하지 않는다. 화면과 서류는
전표 스냅샷을 읽고, 감사와 마스터 연결은 ID를 쓴다. 이관 진단은 `lineKind=item`인데 `itemId`가
없는 줄만 오류로 잡아야 하며, 정상 계정 줄까지 이름으로 억지 연결하면 안 된다.

## 4. 거래처 단가·과세와 품목 원가

`partner_item`은 **현재 거래조건**이다. `partnerId + itemId + Direction`이 연결을 정하고,
`price`는 세금 포함 단가, `taxType`은 거래처별 과세·면세, `Account_Code`는 기본 계정과목이다.
같은 품목도 거래처가 다르면 과세 여부와 단가가 다를 수 있다.

금액 계산은 [lineAmount.ts](../src/shared/lineAmount.ts)만 쓴다.

- `lineAmount(qty, price, exempt)`: 세금 포함 입력에서 공급가액·세액·합계를 확정한다.
- `costFromPurchaseLine(line)`: 매입 전표의 `supply ÷ qty`로 공급가 기준 원가를 낸다.
- `lineAmountFromSupply(qty, supply, exempt)`: 공급가 기준 원가와 마진에서 견적 판매가를 만든다.

`items.cost`는 현재 공급가 기준 원가 스냅샷이다. 누가 어떤 매입 전표 때문에 원가를 바꿨는지
알 수 있도록 `itemCostHistory`를 추가하는 것이 최종형이다.

| `itemCostHistory` 필드 | 역할 |
|---|---|
| `itemId` | 원가가 바뀐 품목 |
| `beforeCost`, `afterCost` | 변경 전·후 공급가 기준 원가 |
| `effectiveAt` | 원가가 업무상 적용되는 날짜 |
| `recordedAt`, `actorId` | 실제 기록 시각과 작업자 |
| `sourceStatementId`, `sourceLineIndex` | 근거 매입 전표와 줄 |

## 5. 거래명세서와 세금계산서

[docParty.ts](../src/shared/docParty.ts)의 `documentParties`가 공급자·공급받는자를 한 번에 만든다.
거래명세서와 세금계산서 메뉴는 이 모듈만 써야 한다. 현재 거래처 정보와 옛 전표의 표시 이름을
화면마다 다르게 조합하지 않는다.

최종형은 발행할 때 아래 당사자 정보를 `partySnapshot`으로 전표에 저장한다.

```text
name · bizNo · ceo · addr · bizType · bizItem · tel · fax
```

그러면 거래처관리에서 주소나 대표자를 나중에 바꿔도 과거 서류가 바뀌지 않는다. 과세 줄 발행은
`taxIssuedAt`, 면세 줄 발행은 `exemptIssuedAt`에 따로 남긴다. 한 전표에 과세와 면세가 섞이면 두
서류를 각각 발행할 수 있어야 한다.

현재 시각 필드 두 개만으로는 여러 전표 묶음 발행, 일부 실패, 홈택스 승인번호와 실제 발행 금액을
감사하기 어렵다. 최종형은 `taxIssueRecords`에 `id`, `kind`, `statementIds`, `supply`, `tax`,
`issuedAt`, `externalApprovalNo`, `status`, `error`를 남기고, 전표의 두 시각은 빠른 목록 표시용으로만
쓴다. 여러 전표의 발행 상태를 바꿀 때도 한 batch로 처리한다.

## 6. 거래처 원장과 통계

거래처 잔액은 전표 유형이 아니라 분개의 채권·채무 계정으로 센다.

- 매출채권: 108 외상매출금
- 지급채무: 251 외상매입금과 253 미지급금
- `allPartnerBalances`: 거래처 전체 미수·미지급 목록
- `buildPartnerLedger`: 한 거래처의 시간순 발생·결제·잔액
- `allocatePartnerCash`: 자금을 오래된 미결 전표부터 배분하고 `settlements` 지정분을 반영

날짜 필터는 행만 자르지 않는다. `from` 이전 변동 합계를 기초로 세우고 기간 안 발생과 결제만
표시한다.

```text
기초 + 기간 발생 - 기간 결제 = 기말
8월 31일 기말 = 9월 1일 기초
```

거래처 통계도 별도 금액 계산을 만들지 않고 같은 분개와 잔액 결과에서 매출·매입·이익률·미수·
미지급을 투영한다.

## 7. 재무제표

`buildJournals`가 `issuedStatements`, `cashEntries`, 계정과목, 기초잔액, 월말 재고 스냅샷을 받아
`JournalEntry[]`를 만든다. 모든 분개는 차변 합계와 대변 합계가 같아야 한다. 계정 누락이나 차대
불일치는 `skipped`로 숨기지 말고 화면과 진단에서 드러낸다.

- 손익계산서: `computeMonthPLFromJournals`
- 재무상태표: 분개 누계와 기초잔액
- 현금흐름표: `computeCashFlowDirect`
- 시산표: 계정별 차변·대변 및 전체 균형 검증

재무제표가 전표 합계나 `fixedCosts`를 직접 더하는 우회 계산은 두지 않는다.

## 8. 구현 순서

1. 매입 전표 줄 `itemId` 이관을 완료하고 무연결 줄을 0건으로 만든다.
2. `StatementCommand`와 순수 검증·정규화 함수를 만든다.
3. 발행 본문·주문 연결·거래처 단가·원가 이력을 원자 저장하고 `operationId` 중복 시험을 붙인다.
4. 알림·외부 전송용 후처리 작업과 재시도 상태를 만든다.
5. `lineKind`, `partySnapshot`, `itemCostHistory`, `taxIssueRecords`, 전표 수정 이력을 추가한다.
6. 거래처 원장에 기간 기초 계산과 날짜 필터를 넣는다.
7. 거래처 통계와 재무제표가 분개 공용 경로만 쓰는지 회귀시험으로 잠근다.
8. 안정화 뒤 이름 매칭·직접 합산·옛 필드를 제거한다.

DB 컬렉션이나 필드를 추가할 때는 별도 이관 스크립트에 `--dry`, `--apply`, `--undo`, 백업을 갖추고
[DB-CHANGELOG.md](../DB-CHANGELOG.md)에 기록한다.

## 9. 현재 코드 구조에서 확인된 문제

2026-09-10 기준 주요 파일은 다음 크기다.

| 파일 | 줄 수 | 한 파일에 섞인 책임 |
|---|---:|---|
| `AdminApp.tsx` | 4,833 | 앱 껍데기, 메뉴, 회사 선택, 거의 모든 업무 저장, 재고 계산, 화면 조립 |
| `TradeStatement.tsx` | 3,904 | 전표 목록, 작성, 수정, 수금·지불, 일반전표, 단가 수정, 인쇄, PDF·엑셀 |
| `ProfitAnalysis.tsx` | 2,055 | 손익, 거래처 통계, 재고평가, 계정 설정, 현금흐름 |
| `TaxStatement.tsx` | 946 | 조회, 묶음 선택, 금액 편집, 발행 상태, 인쇄·PDF, 발행 이력 |
| `cashLedger.ts` | 567 | 계좌 원장, 전표 배분, 거래처 원장, 거래처 잔액, 월별 현금 집계 |
| `types.ts` | 1,278 | 주문·품목·인사·재고·전표·회계의 모든 타입 |

이 구조에서는 다음 문제가 생긴다.

1. 화면 컴포넌트가 Firestore 저장 순서까지 결정하므로 원자 저장을 만들기 어렵다.
2. `TradeStatement`가 약 45개의 로컬 상태를 따로 들고 있어 초기화 누락과 모드 간 잔존값이 생기기 쉽다.
3. `AdminApp`에서 수십 개 배열과 저장 콜백을 자식으로 전달해 작은 변경도 앱 전체에 번진다.
4. `useAppData`가 현재 메뉴와 무관한 컬렉션까지 구독하므로 초기 읽기와 최상위 재렌더가 커진다.
5. `buildJournals`와 잔액 계산을 여러 화면이 각각 만들고 있어 같은 입력을 반복 계산한다.
6. `src/shared`에 약 190개 파일이 평면으로 놓여 도메인 소유권을 찾기 어렵다.
7. `setBomIndex`, `setPackIndex`처럼 렌더 중 전역 인덱스를 바꾸는 숨은 상태가 있다. 함수 입력이나
   명시적 Provider로 바꿔야 시험과 동시 화면이 서로 영향을 주지 않는다.
8. 화면에서 직접 만든 인쇄 HTML과 저장 객체가 커서 표시 변경이 저장 규칙까지 건드리기 쉽다.

infrastructure만 Firestore를 알고, 화면은 application 명령과 조회 hook만 부른다.

## 11. 기존 대형 파일을 나누는 기준

### `AdminApp.tsx`

최종적으로 메뉴와 화면 조립만 남겨 300줄 안팎으로 만든다.

- `AdminShell`: 레이아웃과 회사 전환
- `AdminNavigation`: 메뉴 정의와 권한 표시
- `AdminRoutes`: 현재 메뉴의 lazy 화면 선택
- 각 기능의 Provider 또는 hook: 해당 메뉴가 열렸을 때만 필요한 데이터를 구독
- 각 application service: 저장 순서, transaction, 오류 결과

현재 `AdminApp` 안의 BOM·원가 롤업, 주문 상태 변경, 전표 저장 콜백을 각각의 기능으로 옮긴다.

### `TradeStatement.tsx`

아래를 독립시킨다.

- `StatementPage`: 목록과 작성 창을 여는 상태만 관리
- `StatementHistoryPanel`: 기간·거래처·계정 필터와 페이지네이션
- `StatementComposerDialog`: 작성 흐름을 조립
- `useStatementDraft`: 45개 `useState` 대신 하나의 명시적 draft와 reducer
- `StatementLineTable`: 품목·계정 줄 편집
- `StatementItemPicker`: 거래처 연결 품목·단가·과세 선택
- `StatementDetailDialog`: 발행 전표 조회
- `statementPrintModel`과 출력기: React 상태를 참조하지 않는 문서 모델
- 기존 `OrderPicker`와 `VoucherComposer`: 각자 화면 역할은 유지하되 저장은 application service로 이동

`TradeStatementProps`에 수십 개 저장 콜백을 넘기지 않는다. `StatementService`와 조회 결과를 넘기거나
기능 Provider에서 받는다.

### `ProfitAnalysis.tsx`

현재 여섯 탭을 각각 페이지로 만든다.

- 손익 분석
- 거래처 통계
- 재고 평가
- 계정과목 설정
- 현금흐름
- 정기비용 관리

각 화면은 JSX와 필터 상태만 갖고 계산은 `accounting/projections`에서 받는다. 거래처 통계가 전표를
직접 filter/reduce하지 않게 한다.

### `TaxStatement.tsx`

조회, 작성, 발행 이력, 출력으로 나눈다. 금액 합치기는 순수 함수, 발행 처리는 `applyTaxIssue`,
인쇄는 공용 `DocPartySnapshot`과 출력 모델을 쓴다.

### `cashLedger.ts`와 `types.ts`

`cashLedger.ts`는 계좌 원장, 결제 배분, 거래처 원장 투영을 각각 분리한다. `types.ts`는 한 번에
옮기지 말고 기능을 이동할 때 그 기능 타입도 같이 옮긴다. 외부 import가 깨지지 않도록 전환 기간에는
옛 파일에서 새 타입을 재수출한다.

## 12. 구독과 계산 최적화

### 화면별 데이터 구독

`useAppData` 한 벌 대신 다음처럼 나눈다.

- `useReferenceData`: 회사, 품목, 거래처처럼 여러 화면이 쓰는 작은 기준정보
- `useOrdersData(range)`: 주문 화면이 열릴 때 주문 범위 구독
- `useStatementBook(companyId, range)`: 전표 목록과 필요한 앵커·미결 전표
- `useAccountingBook(companyId, period)`: 전표·자금·기초·재고 스냅샷
- `useOfficeTalkData`: 오피스톡을 열었을 때만 공지·채팅 구독
- `useInventoryData`: 재고 메뉴가 열렸을 때만 로트·원장 구독

인증과 회사가 정해진 뒤에만 구독하고, 화면이 닫히면 unsubscribe한다. 전표·자금처럼 누적 잔액이
필요한 데이터는 연말 앵커 이후와 현재 기간만 읽는다.

### 계산 한 번, 화면은 여러 번 사용

`AccountingBookProvider` 또는 동등한 query cache가 아래 결과를 한 번 만든다.

```text
merged vouchers
  → journalEntries + skipped
    → partnerBalances
    → partnerLedger(period)
    → partnerStats(period)
    → financialStatements(period)
```

`issuedStatements`나 `cashEntries` 배열의 내용이 바뀌었을 때만 다시 계산한다. 지금 데이터 양에서는
분개를 Firestore에 별도 저장해 진실을 두 벌로 만들 필요는 없다. 먼저 메모리 계산을 공유하고,
연말 앵커와 기간 조회로 입력량을 줄인다.

### 파일 크기 목표

줄 수는 규칙이 아니라 경고등으로 쓴다.

- 앱 껍데기·페이지: 보통 150~350줄
- 복잡한 입력 화면: 보통 300~600줄
- 순수 업무 모듈: 한 가지 불변식을 설명할 수 있는 크기
- 800줄을 넘으면 서로 다른 변경 이유가 섞였는지 반드시 검토

큰 파일을 작은 JSX 조각으로만 쪼개고 동일한 40개 props를 계속 전달하면 구조는 그대로다. 저장
명령과 계산을 먼저 분리한 뒤 화면을 나눠야 효과가 있다.

## 13. 안전한 리팩터링 순서

한 번에 전부 옮기지 않는다. 다음 단계마다 기존 시험을 통과시키고 동작을 비교한다.

1. 현재 전표·잔액·손익 결과를 고정하는 특성 시험을 보강한다.
2. 인쇄·엑셀·금액 합산 같은 순수 함수를 `TradeStatement` 밖으로 옮긴다.
3. `StatementDraft` reducer와 작성 UI를 분리한다. 저장 방식은 아직 바꾸지 않는다.
4. `StatementCommand`와 Firestore repository를 만들고 필수 저장을 transaction으로 바꾼다.
5. 전표 목록·상세·작성 화면을 분리하고 거대 props를 없앤다.
6. `cashLedger.ts`의 세 계산 영역과 `ProfitAnalysis`의 탭을 분리한다.
7. `AccountingBook` 계산 결과를 화면들이 공유하게 한다.
8. `useAppData`를 화면별 구독으로 바꾸고 `AdminApp`을 껍데기로 줄인다.
9. 안정화된 기능부터 `types.ts`와 평면 `shared` 파일을 기능 폴더로 옮긴다.
10. 마지막에 호환 재수출과 죽은 콜백·옛 필드를 제거한다.

각 단계의 커밋은 파일 이동과 동작 변경을 가능하면 분리한다. 그래야 문제가 생겼을 때 어느 변경이
원인인지 찾고 되돌릴 수 있다.
