# 복사주문 확정 결과 보존과 승인 규칙 연결

## 현재 단계

2026-10-14 구현과 최종 검증을 완료했다. 기존 최초 원문 보관 모델 5파일을 실제 복사주문 저장, 관리자 승인, 승인 규칙을 사용하는 판독에 연결했다. 앱·서버 타입 검사, 양 앱 빌드, 집중 시험, 실제 로컬 Auth·Firestore·callable HTTP·Rules 검증과 실제 컴포넌트 화면 검수를 통과했다. 배포 결과와 TODO019 전체 수용 판정은 MEMORY의 최신 상태에 기록한다.

## 최초 요청과 실제 주문

복사한 전체 원문, 최초 판독 결과, 입력행, 사람이 확정한 전체 주문 초안, 주문·행 ID와 번호를 송신 전에 고정한다. 회사와 사용자별 저장에서 최초 문자열을 보존하고 같은 내용으로만 재시도한다. 일반 직접 주문의 번호·수량·단위 계산은 기존 함수를 사용한다.

`submitOrderCopyCommand`는 회사·계정·권한과 허용 필드를 검증하고 `orders`와 서버 전용 `orderCopyOperations`를 같은 transaction으로 저장한다. 같은 요청의 완료 영수증은 수정되거나 삭제된 주문을 다시 생성하지 않는다. 확정 거절도 최초 요청과 함께 보존하며, 영수증이 없다는 이유로 미반영을 추정하지 않는다.

## 제안과 관리자 승인

확정 품목의 `orderedAs`와 품목 ID를 최초 입력행의 원문·수량·박스 선택과 대조한다. 양끝·연속 공백을 정리하고, 검증된 마지막 수량과 단위만 분리한다. `350ml`, `1L`, `kg` 같은 규격을 제거하거나 모호한 문장을 추측하지 않는다.

회사·거래처·별칭·품목이 같은 서로 다른 완료 캡처 3건과 주문 3건을 제안 근거로 사용한다. `reviewOrderInterpretationRuleCommand`는 관리자 권한과 근거 원문·해시·revision을 다시 확인하여 승인하거나 중지한다. 중지된 규칙은 새 캡처로 자동 승인하지 않는다.

`listOrderInterpretationRulesCommand`로 받은 승인 규칙을 실제 판독에 연결한다. 불명확하거나 충돌한 연결은 추천하지 않는다. 기존 최초 판독 모델은 호환을 유지하며 판독 가능한 근거가 없는 과거 자료는 학습하지 않는다.

## 보호와 검증

`orderCopyOperations`와 `orderInterpretationRules`는 포괄 client 허용에서 제외하고 직접 조회·쓰기를 막는다. 직원의 저장·승인 규칙 조회와 관리자의 승인·중지는 각각 서버에서 회사와 역할을 확인한다.

집중 시험과 실제 로컬 SDK/RPC/Rules 검증은 중복·응답 유실·다른 계정·수정/삭제 후 재시도·승인 전후 판독을 확인한다. 운영 자료와 실제 Gemini·신규 외부 API는 검수에 사용하지 않으며, 민감 원문의 90일 보존 정책은 새로 정하지 않는다. 기존 클라이언트 번호를 최초 한 번 고정하는 범위이며 전역 번호 경합 해결로 확대하지 않는다.
